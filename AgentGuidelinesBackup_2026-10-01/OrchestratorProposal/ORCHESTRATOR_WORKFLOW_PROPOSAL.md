# BathhouseSim 오케스트라 워크플로우 제안

## 상태와 목적

- 상태: 논의안. 아직 `AGENT_WORKFLOW.md`를 대체하거나 에이전트 권한을 변경하지 않는다. 현재 정본은 `AGENTS.md`, `.md/AGENT_WORKFLOW.md`와 역할별 `.md/AGENT_*.md`다.
- 목적: 하나의 마스터 대화에서 전문 에이전트 호출, 승인 관문, 재작업, 컨텍스트 전달, 후속 문제 기록과 개선 사이클을 관리하는 방식을 제안한다.
- 전제: Unreal Editor 작업은 `.md/UnrealEditorWorkflowDraft/`의 통합 역할 초안을 기준으로 한다. 이 제안은 MCP 전용 역할(`AGENT_UNREAL_MCP.md`)과 별도 Python 역할(`AGENT_UNREAL_PYTHON.md`)이 폐기되고 범용 Unreal Editor 역할(`AGENT_UNREAL_EDITOR.md`)로 교체된 상태를 가정한다. Editor 실행 규칙이 이 제안과 다르면 통합안을 우선한다. 단, 통합 리뷰 단계 제외와 PIE 검증 제외는 이 제안이 우선한다.
- 이 제안서는 합의 내용의 완결성을 우선하며 공통 정책 문서의 200줄 제한을 적용하지 않는다. 채택할 때는 내용 삭제 대신 안정적인 책임 단위로 문서를 분리한다.

## 기본 원칙

1. 마스터 모드는 사용자가 오케스트레이션 Skill로 명시적으로 시작한 세션에서만 동작한다. 새 세션이라고 자동으로 마스터가 되지 않는다.
2. 마스터 세션에서는 사용자가 단계나 에이전트 이름을 지정하지 않아도 되며 마스터가 요청 의도와 현재 상태로 선택한다.
3. 기능 명세 승인 뒤에는 차단 사유가 없는 한 설계부터 Editor 작업까지 자동으로 연결한다.
4. PIE 검증은 항상 사람이 수행한다. 에이전트는 PIE를 시작하거나 PIE에서 입력·시나리오를 검증하지 않는다. 별도의 통합 리뷰 단계는 두지 않는다.
5. 대화는 편의용 컨텍스트이고 단계 간 정본 전달은 작업별 폴더의 결과물과 프로젝트 정본 문서로 수행한다.
6. 전문 에이전트는 역할 범위를 넘지 않으며, 후속 문제는 유입·검출 실패 단계를 구분해 일반화된 교훈만 미래 에이전트에 제공한다.
7. 정책 문서는 역할별 요구 수준만 정하고 특정 실행 도구·모델 이름에 묶이지 않는다.

## 사용자 요청 자동 분류

이 분류는 마스터 세션에서만 적용한다. 마스터가 아닌 세션의 사용 방식은 `마스터 세션과 일반 세션` 절을 따른다.

| 사용자 요청 | 마스터가 선택할 시작 단계 |
|---|---|
| 신규 기능 구현 | 기능 명세 |
| 원인과 해결법만 요청 | 관련 Source 읽기와 Unreal Editor 읽기 전용 조사 모드로 진단 |
| 승인된 범위의 코드 수정 | 구현 |
| Editor 작업 요청 | 코드 리뷰 상태 확인 후 Unreal Editor 작업 모드 |
| 화면 조작 명시 요청 | Unreal Editor 역할의 화면 작업 모드 진입 조건 확인 |
| 코드 검토 | 코드 리뷰 |
| 코드와 asset의 실제 일치 확인 | Unreal Editor 읽기 전용 조사 모드(코드 계약 대조 포함) |
| PIE 검증 통과 보고 | 작업 완료 처리 |
| 진행 중 작업의 PIE 실패 보고 | `BugReports/`에 현상 기록 후 그 작업 폴더 안에서 진단·재작업 |
| 완료된 작업에서 나중에 발견한 버그·의도 불일치 보고 | `BugReports/`에 현상 기록 후 새 `BUG-` 작업 |
| 진행 중 작업 재개 | 작업 폴더의 결과물 첫머리와 `CONTEXT.md`로 현재 단계 판정 |

- 요청이 어느 작업에 속하는지 먼저 정한다. 기존 작업 폴더에 속하면 그 작업 ID로 이어 가고, 아니면 새 작업 ID와 폴더를 만든다.
- 사용자가 단계를 잘못 지정해도 마스터가 진입 조건을 확인하고 올바른 단계로 교정한다.
- 진단 요청은 수정 권한으로 확대하지 않고, 수정 요청은 승인된 기능·설계 범위 안에서만 실행한다.
- 새로운 사용자 동작이나 결과를 결정해야 하면 기존 구현을 임의로 확장하지 않고 기능 명세로 돌린다.

## 마스터 오케스트레이터 책임

- 요청을 분류하고 대상 작업 폴더, 현재 단계의 진입 조건과 필수 결과물을 확인한다.
- `작업 ID + 역할` 단위로 하위 에이전트를 관리하고 재개 또는 신규 생성을 판단한다.
- 새 사용자 결정과 중요한 변경사항을 관련 문서 또는 후속 메시지로 전달한다.
- 리뷰 실패는 구현, 구조 문제는 아키텍처, 동작 불일치는 기능 명세로 돌려보낸다.
- Editor 실행 수단(MCP, Python, 보조 도구) 선택은 Unreal Editor 역할에 맡기고, 수단 전환을 이유로 다른 에이전트에 재분배하지 않는다.
- Computer Use 화면 작업 모드는 다른 자동화 경로를 모두 시도한 뒤 마지막에만 쓰며, 작업 직전에 사용자 승인을 받는다.
- 사용자 승인 관문, 외부 권한과 실제 차단 사유에서만 자동 진행을 멈춘다.
- Editor 작업 뒤 기능 계약, 코드 리뷰 결론과 저장된 Editor 상태 보고의 일치를 문서로 확인하고 사용자 PIE 체크리스트를 전달한다. PIE 결과는 사용자 보고로 받아 완료 또는 문제 분류로 처리한다.

## 작업 ID와 작업 폴더

### 작업 ID

- 작업은 기능 명세부터 사용자 PIE 검증까지 한 벌의 단계 결과물을 가지는 단위다. 수직 구현 단위, 전체 확장 단계, 단순 버그 수정이 각각 하나의 작업이다.
- 여러 구현 단위로 나뉘는 기능은 상위 작업 ID 아래 단위 작업 ID를 둔다. 예: 상위 `SERVICE`, 단위 `SERVICE-U4`.
- 버그 수정 작업 ID는 버그 리포트 파일명에서 만든다. 예: `BUG-2026-10-01_litter_tongs_false_take_highlight`. 새 `BUG-` 작업은 이미 완료된 작업에서 나중에 발견한 버그에만 만든다. 진행 중 작업의 PIE 실패는 버그 리포트만 쓰고 그 작업 폴더 안에서 재작업한다.
- 한 번 정한 작업 ID는 바꾸지 않는다. 시나리오 ID(`TRSH-001` 등)와 별개다.

### 작업 폴더

현재 `NextWork/` 방식을 일반화해 작업마다 폴더를 둔다.

```text
.md/Work/
├─ SERVICE/                       상위 기능: 전체 명세·QNA·CONTEXT
│  ├─ CONTEXT.md
│  ├─ PROMPT_ARCHITECTURE.md      전체 기능 명세(참조 정본)
│  ├─ QNA_FEATURE_SPEC.md
│  └─ SERVICE-U4/                 구현 단위: 이 단위의 단계 결과물 일체
│     ├─ CONTEXT.md
│     ├─ PROMPT_ARCHITECTURE.md
│     ├─ PROMPT_IMPLEMENTATION.md
│     └─ ...
└─ BUG-2026-10-01_litter_tongs_false_take_highlight/
   ├─ CONTEXT.md
   ├─ PROMPT_IMPLEMENTATION.md
   └─ ...
```

- 지금 `.md/` 루트에 하나씩 있는 단계 결과물(`PROMPT_*.md`, `QNA_*.md`, `REPORT_UNREAL_DISCOVERY.md`)은 이름을 유지한 채 작업 폴더 안으로 옮긴다. 루트에는 작업별 결과물을 두지 않는다.
- `하나의 결과물은 하나의 작업만 기록` 규칙은 폴더 단위로 지킨다. 여러 작업이 동시에 진행·보류 상태일 수 있다.
- 작업 폴더는 공유 정본이 아니다. `Architecture/*`, `Unreal/*`, `USER_UNREAL.md`, `BugReports/`, `FEEDBACK_BACKLOG.md`는 루트 공유 위치에 둔다.
- `PIE_CHECKLIST.md`는 마스터가 작성하는 작업별 사용자 PIE 체크리스트다.
- `USER_UNREAL.md` 항목에는 작업 ID를 붙여 어느 작업의 Editor 작업 완료를 막는지 표시한다.
- `CONTEXT.md`에는 작업 목표, 상위·선행·관련 작업, 결과물 목록, 현재 단계와 재개 지점, 사용자 작업 지시 요약, 기능 명세 승인 일자와 받은 사전 허용, 리뷰 회차·아키텍처 자동 복귀 사용 여부, 워커 세션 ID(Codex 재개용)만 둔다. 결정의 정본은 QNA와 단계 결과물이며 둘이 다르면 정본이 우선한다.
- `CONTEXT.md`는 마스터가 갱신한다. 마스터 없이 단계를 직접 실행하면 그 단계가 재개 지점만 갱신한다.
- 사용자 PIE 검증 통과, 정본 반영과 커밋을 확인한 뒤 작업 폴더를 제거하고 이력은 Git에 맡긴다. 상위 작업 폴더는 모든 단위가 끝난 뒤 제거한다.

### 결과물 첫머리 형식

작업 폴더의 모든 단계 결과물은 제목 바로 아래에 다음 세 줄을 같은 순서로 둔다.

```markdown
# <결과물 종류> — <작업 이름>

- 작업 ID: `SERVICE-U3`
- 단계: Editor 작업
- 상태: 보류 — USER_UNREAL.md의 external actor 저장 미완료(Unreal Editor), 해소 후 Editor 작업 재개
```

| 상태 | 의미 |
|---|---|
| 진행 | 소유 단계가 아직 작성·작업 중이다. 다음 단계 입력으로 쓰지 않는다. |
| 완료 | 소유 단계의 결론이 확정됐다. 다음 단계 입력으로 쓸 수 있다. |
| 보류 | 작업이 멈췄다. 같은 줄에 사유, 책임 단계와 재개 조건을 적는다. |

- 단계 값은 정규 흐름의 단계 이름을 쓴다: 기능 명세, Editor 사전 조사, 아키텍처, 구현, 코드 리뷰, Editor 작업, 사용자 PIE 검증.
- 소유 단계만 자기 결과물의 첫머리를 바꾼다. 마스터와 리뷰는 남의 결과물 상태를 고치지 않고 `CONTEXT.md`나 자기 결과물에 판단을 남긴다.
- 에이전트는 시작할 때 입력 결과물의 작업 ID가 지시받은 작업 폴더와 같고 상태가 완료인지 확인한다. 다르면 자동 진행 중단 조건으로 처리한다.
- 재작업 프롬프트(`PROMPT_IMPLEMENTATION_R.md`, `PROMPT_UNREAL_R.md`)는 세 줄 아래에 출처 한 줄을 더 둔다. 예: `- 출처: 코드 리뷰 2회차`, `- 출처: 사용자 PIE (BugReports/<파일>)`. 마스터는 이 줄로 리뷰 루프 횟수와 PIE 재작업 횟수를 나눠 센다.

## 역할별 요구 수준

| 역할 | 추론 수준 | 실행 도구 | 에이전트 연속성 | 필요한 실행 능력 |
|---|---|---|---|---|
| 마스터 오케스트레이터 | 높음 | Claude (사용자 세션) | 마스터 대화 유지 | 하위 에이전트 호출·재개, 문서 읽기·쓰기 |
| 기능 명세 | 높음 | Claude | 같은 작업은 재개 | 문서 읽기·쓰기 |
| Unreal Editor (조사·작업·화면 작업 모드) | 높음 | Claude | 같은 작업은 재개 | Unreal MCP, Editor Python, headless commandlet, 승인 시 native 화면 관찰·입력 |
| 아키텍처 | 높음 | Claude | 같은 작업은 재개 | 문서·Source 읽기 |
| C++ 구현 | 높음 (대체 시 중간) | Codex (`codex exec`), GPT 사용 한도 도달 시 Claude 대체 구현 | 자신의 구현 후속 수정은 `codex exec resume`으로 재개, 대체 뒤에는 Claude 대체 구현 에이전트 재개 | Source 쓰기, UE `Build.bat`, headless Automation |
| 코드 리뷰 | 높음 | Claude | 첫 리뷰·PIE 실패 진단·설계 변경 후는 새 에이전트, 같은 리뷰어의 지적에 따른 재작업 후는 그 리뷰어 재개 | Source 읽기, 빌드·테스트 실행 |
| 회고·피드백 일반화 | 높음 | Claude | 사용자 요청 시에만, 독립된 새 에이전트 | 문서·버그 기록·Git 이력 읽기 |

- 정책 문서는 모델 이름을 기록하지 않는다. 구체적인 모델과 추론 설정은 실행 도구별 설정(Claude Code `.claude/agents/*.md` frontmatter, Codex `~/.codex/config.toml`)이 소유한다.
- 도구별 설정은 위 요구 수준을 만족하도록 연결하며, 요구 수준 자체를 바꾸지 않는다.
- Unreal Editor 역할은 높음으로 둔다(2026-10-01 사용자 지정). 근거는 통합 역할이 실행 중에 경로 선택, 저장 성공 판정, 예상 밖 dirty package 구분과 실패 분류를 직접 하고, 통합 리뷰가 없어 그 판단이 PIE 전 마지막 에이전트 검증이 된다는 점이다. 한 에이전트가 모드를 오가므로 화면 작업 모드도 같은 설정을 쓴다.
- 작업 난이도에 따른 자동 추론 상·하향은 사용하지 않는다. 아래 구현 대체는 난이도가 아니라 도구 사용 한도에 따른 사용자 지정 규칙이다. 요구 수준 변경은 사용자의 명시적 요청 또는 워크플로우 정책 개정으로만, 모델 연결 변경은 해당 도구 설정 개정으로만 수행한다.

### 워커 모델 고정 방식

마스터는 Claude다. 워커의 모델과 추론 수준은 마스터가 호출할 때마다 고르지 않고, 도구별 설정 파일에 역할별로 고정한다.

- Claude 워커는 역할마다 `.claude/agents/<역할>.md` 정의 파일을 둔다. frontmatter의 `model`과 `effort`로 위 요구 수준을 연결한다. 요구 수준 `높음`은 `model: opus`, `effort: high`로 연결한다. 구현 대체 역할은 `model: claude-sonnet-5-5`, `effort: medium`으로 연결한다. 사용자가 지정한 버전에 고정하기 위해 계열 이름 대신 전체 모델 ID를 쓴다.
- 정의 파일 본문은 규칙을 복제하지 않고 해당 `.md/AGENT_*.md`와 `AGENT_WORKFLOW.md`를 읽으라는 안내만 둔다. `tools`, `mcpServers`로 역할에 필요한 도구만 연다. 예: 코드 리뷰는 수정 도구 제외, MCP는 Unreal Editor 역할만.
- Claude 워커의 모델은 호출 시 `model` 값, 정의 파일 `model`, `CLAUDE_CODE_SUBAGENT_MODEL` 환경 변수, 마스터 모델 순으로 정해진다. 마스터는 호출할 때 `model` 값을 넘기지 않아 정의 파일 설정이 적용되게 한다. 사용자가 지시한 경우만 예외다.
- 모든 설정을 덮어쓰는 `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`는 쓰지 않는다.
- Codex 워커는 `~/.codex/config.toml`의 `model`과 `model_reasoning_effort`를 따르며, 마스터는 `codex exec` 호출 때 `-m`이나 추론 수준을 덮어쓰지 않는다. 사용자가 지시한 경우만 예외다.
- 마스터는 Codex 워커를 `codex exec -C <프로젝트> -o .md/Work/<작업 ID>/<보고 파일> "<인계 패킷>"`으로 부르고 `-o` 최종 보고만 읽는다. 재작업은 `CONTEXT.md`에 적은 세션 ID로 `codex exec resume`한다.

### 실행 도구 선택 기준

- 구현과 그 구현의 코드 리뷰는 서로 다른 모델 계열이 맡는다. 현재 분담은 구현 Codex, 코드 리뷰 Claude다. 구현 대체 중에는 예외로 한다.
- 기능 명세와 사용자 질문이 오갈 수 있는 작업은 Claude가 맡는다. `codex exec`는 실행 중에 사용자에게 질문하거나 승인을 받을 수 없다.
- Unreal Editor 역할은 한 도구가 맡는다. Editor 세션 소유권·MCP 세션·화면 작업 모드를 두 도구가 나눠 가지지 않는다.
- 한 작업 안에서 한 역할에 정한 도구는 바꾸지 않는다. 예외는 두 가지다. 같은 지적이 반복돼 루프 한도에 걸렸을 때 아키텍처 복귀 전에 다른 계열 에이전트로 한 번 교체하는 경우와, 아래 구현 대체다.

### 구현 대체 (GPT 사용 한도)

- 구현 전이나 구현 중에 GPT(Codex) 사용 한도에 도달하면, 구현은 Claude 대체 구현 에이전트(`claude-sonnet-5-5`, `effort: medium`)로 진행한다. 사용자에게 다시 묻지 않는다.
- 구현 중에 대체되면 대체 에이전트는 현재 작업 트리에서 이어서 구현한다.
- 그 밖의 단계, 결과물과 검증 절차는 바뀌지 않는다. 대체 중에는 구현과 코드 리뷰가 같은 Claude 계열이 되는 것을 허용한다.

## 정규 실행 흐름

```text
요청 → 기능 명세 → 선택적 Editor 사전 조사 → 사용자 명세 승인
→ 아키텍처 → 구현 → 코드 리뷰 → Editor 작업(필요 시 마지막에 승인받은 화면 작업 모드)
→ 마스터 인계 확인 → 사용자 PIE 검증 → 완료 또는 문제 분류·복귀
```

- 기능 명세 승인 전에는 설계와 구현을 시작하지 않는다.
- 승인 후 `설계 → 구현 → 코드 리뷰 → Editor 작업`은 별도 사용자 호출 없이 이어서 진행한다.
- Editor 작업이 끝나면 마스터는 기능 시나리오, 코드 리뷰 결론과 Editor 저장 결과 보고가 서로 맞는지 문서로 확인한 뒤 PIE 체크리스트를 사용자에게 넘긴다. 이 확인은 별도 에이전트 단계가 아니다.
- Content 변경이 없는 작업도 PIE 검증은 사용자가 수행한다.
- 질문, 구현·코드 리뷰 루프 한도 초과 또는 사용자 승인 관문에서는 중단하고 정확한 재개 조건을 결과물 첫머리와 `CONTEXT.md`에 남긴다.

## 자동 진행과 중단 조건

다음 단계의 진입 조건, 입력 결과물과 권한이 충족되면 마스터는 사용자에게 다시 실행을 요청하지 않고 다음 에이전트를 호출한다. 전문 에이전트가 완료 보고를 반환했다고 해서 다음 단계가 자동 승인된 것은 아니며 마스터가 결과물과 결론을 확인한다.

자동 진행을 중단하는 조건은 다음과 같다.

- 사용자 결과가 달라지는 선택이 남음
- 기능 명세 승인 또는 사용자 PIE 검증이 필요함
- 구현·코드 리뷰 루프 한도를 넘었고 아키텍처 자동 복귀도 이미 사용함
- 리뷰가 기능 명세 재검토를 결정함(사용자 동작 결정 또는 명세 재승인 필요)
- 화면 작업 모드 사용 승인이 필요함(작업 직전에 매번)
- 사전 허용 밖의 승인 범위 밖 asset 수정이 필요함
- 사용자 소유 변경과 충돌하거나 새로운 외부 권한이 필요함
- 결과물의 작업 ID, 시나리오 ID 또는 현재 단계가 서로 일치하지 않거나 입력 결과물이 완료 상태가 아님

중단 보고에는 완료된 범위, 책임 단계, 차단 근거, 필요한 사용자 결정과 재개 지점을 포함한다.

자동화로 완료할 수 없는 Editor 항목은 자동 구간을 멈추지 않는다. Editor 작업이 끝난 뒤 PIE 체크리스트와 함께 한 번에 사용자에게 넘긴다.

### 구현·코드 리뷰 루프

```text
구현 → 리뷰 1 ─실패→ 재작업 1 → 리뷰 2 ─실패→ 재작업 2 → 리뷰 3
                                                       └ 실패 → 자동 루프 종료, 마스터 분류
```

- 코드 리뷰 실패에 따른 구현 재작업은 작업당 최대 2회까지 사용자 호출 없이 자동으로 진행한다.
- 세 번째 리뷰도 실패하면 마스터가 원인을 분류한다.

| 상황 | 처리 |
|---|---|
| 같은 지적이 반복됨 | 설계 모호로 보고 아키텍처로 자동 복귀, 이후 구현은 새 구현 에이전트 |
| 매번 새로운 지적이 나옴 | 범위 과대로 보고 아키텍처로 복귀해 작업 분할 |
| 사용자 동작을 정해야 함 | 기능 명세로 복귀하고 사용자에게 질문 |

- 아키텍처 복귀는 작업당 1회까지 자동으로 진행하고, 복귀 뒤 루프는 횟수를 새로 센다. 복귀 뒤에도 한도에 다시 걸리면 사용자에게 보고하고 멈춘다.
- 같은 지적이 반복될 때는 아키텍처 복귀 전에 구현을 다른 모델 계열 에이전트로 한 번 교체해 볼 수 있다.
- 마스터는 리뷰 회차와 아키텍처 자동 복귀 사용 여부를 `CONTEXT.md`에 적는다.
- 사용자 PIE 실패에서 시작한 재작업은 리뷰 루프 횟수를 새로 센다. 같은 PIE 항목이 두 번 실패하면 구현이 아니라 설계 문제로 보고 아키텍처 검토로 보낸다.
- 루프 한도와 관계없이, 코드 리뷰가 첫 판단부터 설계나 기능 명세의 문제로 결론 내리면 구현 재작업 없이 바로 해당 단계로 복귀한다.
- 코드 리뷰 또는 Editor 작업에서 기능 명세나 아키텍처 단계로 복귀가 결정되면, 마스터는 복귀를 실행하기 전에 `FEEDBACK_BACKLOG.md`에 상위 단계 복귀 기록을 남긴다(아래 Feedback 절).

## 사람 개입·토큰·시간 최적화

### 사람 개입 줄이기

1. 질문은 추천안과 함께 한 번에 묻는다.
   - 기능 명세 단계는 질문을 한 문서에 묶고 각 질문에 추천안과 이유를 붙인다.
   - 답변은 맨 위 한 줄로 받는다. 예: `답변: 전부 추천안`, `답변: 전부 추천안, 단 Q3 B`.
   - 다른 답에 따라 갈리는 질문은 `연쇄:` 메모로 같은 문서 안에서 처리하고 2차 질문을 만들지 않는다. 답변 뒤 추가 질문은 설계 단계가 찾은 경우에만 만든다.
   - 질문 없이 적용할 전제에는 `P1`처럼 번호를 붙여, 사용자가 같은 답변 줄에 `P3 반대: ...`로 이의를 적을 수 있게 한다.
   - 수치는 질문하지 않고 기본값 표로 제시한다. 플레이 후 Editor 조정값으로 바꾼다.
   - 사용자 동작과 무관한 선택은 `설계에 맡김` 목록으로 분리하고 질문하지 않는다. 아키텍처 단계가 정한다.
2. 명세 승인 때 사전 허용을 함께 받는다.
   - 자동 구간에서 멈출 수 있는 승인 범위 밖 asset 처리와 PIE 통과 후 커밋·병합 여부를 명세 승인과 함께 묻는다. 화면 작업 모드는 사전 허용 대상이 아니며 작업 직전에 따로 승인받는다.
   - 기능 명세 승인은 QNA 답변 줄과 함께 `CONTEXT.md`에 승인 일자로 남기고, 받은 허용은 이 작업에 한해 `CONTEXT.md`에 적는다. 예: `사용자 PIE 통과 후 자동 커밋·병합`.
   - 사전 허용은 다른 작업으로 넘어가지 않는다.
3. 수동 작업과 PIE를 한 번에 넘긴다.
   - Editor 역할은 자동화로 완료할 수 없는 항목을 만나도 멈추지 않고 남은 allowlist 작업을 계속한다. 남은 항목 중 화면 작업으로 처리할 수 있는 후보는 한 번에 모아 사용자 승인을 받고, 승인된 항목을 처리한 뒤 나머지를 `USER_UNREAL.md`에 기록한다.
   - Editor 작업이 끝나면 마스터는 `USER_UNREAL.md` 항목과 PIE 체크리스트를 한 번에 사용자에게 넘긴다. 각 수동 항목에는 먼저 끝내야 하는 PIE 시나리오를 표시한다.
4. PIE 체크리스트는 사람이 빨리 끝낼 수 있게 만든다.
   - 구현과 Editor 단계는 완료 보고에 시나리오 ID별 PIE 관찰 항목을 남기고, 마스터가 이를 작업 폴더의 `PIE_CHECKLIST.md`로 정리한다.
   - 시나리오 ID 순서가 아니라 한 번 플레이하며 따라갈 수 있는 동선 순서로 정렬한다.
   - 각 항목을 `이번 변경`과 `회귀 확인`으로 나누고, 회귀 확인은 영향받는 시스템만 남긴다.
   - 항목마다 기대 결과를 한 줄로 적어 사람은 맞음·틀림만 판단하게 한다.
   - 구현 단계의 headless Automation 테스트(PIE가 아닌 것)는 유지해 사람이 보기 전에 로직 오류를 거른다.
   - 사용자는 `PIE_CHECKLIST.md`에 항목별 통과·실패와 한 줄 메모를 표시하거나 마스터 세션에 `전부 통과`, `5번 실패: …`처럼 짧게 보고한다. 버그 리포트는 마스터가 그 메모로 작성한다. 워커 세션에는 보고하지 않는다.

### 토큰 절약

5. 작업마다 git 브랜치를 두고 단계마다 커밋한다.
   - 작업 브랜치는 `work/<작업 ID>`로 만들고, 구현·코드 리뷰 통과·Editor 작업 등 단계가 끝날 때마다 커밋한다.
   - 결과물 첫머리 또는 `CONTEXT.md`에 단계 시작 커밋을 적고, 리뷰 에이전트는 파일 전체 대신 `git diff <단계 시작 커밋>`을 읽는다.
   - 실패한 단계만 되돌리고, 사용자 PIE 실패 시 코드 단계 커밋과 Editor 단계 커밋을 나눠 비교해 책임 단계를 분류한다.
   - 커밋은 마스터가 하며 메시지는 `[작업 ID] 단계: 요약` 형식이다.
   - 사용자 PIE 통과 후 단계 커밋을 보존하는 방식(`--no-ff`)으로 기본 브랜치에 병합한다. 사전 허용이 없으면 병합 전에 사용자에게 묻는다.
   - Editor가 열린 상태에서는 브랜치를 바꾸지 않는다. 실행 중인 Editor 아래에서 `.uasset`이 바뀌면 asset 손상이나 크래시가 날 수 있다.
   - 작업 브랜치가 진행 중일 때 사용자가 기본 브랜치에서 Content를 바꾸면 마스터에게 알린다. `.uasset`은 바이너리라 자동 병합되지 않는다.
6. 인계할 때 읽을 문서를 명시한다.
   - 마스터는 인계 패킷에 이번 단계에 필요한 시스템 문서 목록과 해당 시나리오 ID 구간을 적는다. 하위 에이전트는 목록 밖 문서를 필요할 때만 추가로 읽고 그 이유를 보고한다.
   - 하위 에이전트의 완료 보고는 결론과 파일 경로 중심으로 20줄 이내로 쓴다. 상세 내용은 작업 폴더 결과물에 둔다.
7. 재리뷰는 원래 리뷰어를 재개한다.
   - 코드 리뷰 실패로 재작업한 뒤의 재검증은 원래 리뷰어를 재개해 이전 지적과 새 diff만 확인한다.
   - 사용자 PIE 실패는 새 리뷰어가 원인을 진단하고, 수정 뒤 재검증은 그 새 리뷰어를 재개한다. 결함을 놓친 원래 리뷰어는 진단하지 않는다. 설계가 크게 바뀐 경우에도 새 리뷰어를 쓴다.
8. 필요 없는 단계는 마스터가 건너뛴다.
   - `PROMPT_UNREAL.md`가 Content 변경 없음을 선언하고 `git status`로 Content가 그대로임을 확인하면 Editor 단계를 생략한다. 마스터가 `PROMPT_UNREAL.md`의 PIE 관찰 항목으로 바로 체크리스트를 만든다.
   - Content와 무관한 작은 버그는 버그 리포트를 기능 계약으로 보고 기능 명세 단계를 생략한다.
   - 생략한 단계와 근거는 `CONTEXT.md`에 적는다.

### 시간 절약

9. 빌드 결과를 재사용한다.
   - 구현자는 `PROMPT_REVIEW.md`에 빌드 시점의 Source 트리 해시와 빌드 로그 경로를 적는다.
   - 리뷰어는 해시가 같으면 다시 빌드하지 않는다. 다르면 다시 빌드한다.
10. Editor 세션을 재사용한다.
    - 한 작업 안의 Editor 사전 조사와 Editor 작업은 같은 Editor 프로세스를 이어 쓴다. 새 프로세스 재로드가 필요한 검증만 따로 실행한다.
    - 사용자가 같은 프로젝트의 Editor를 열어 두었으면 그 세션에서 작업해, 사용자가 재시작 없이 바로 PIE를 할 수 있게 한다.
11. 병렬 실행은 문서 단계만 한다.
    - 코드 단계와 Editor 단계는 한 작업 트리와 한 Editor를 공유하므로 코드·Editor 단계에 있는 작업은 동시에 하나만 둔다.
    - 작업을 전환하려면 현재 단계 경계에서 커밋하고, 현재 작업을 `보류`로 표시하고, Editor를 닫았거나 dirty package가 없음을 확인한다. 다른 작업이 끼어드는 것은 사용자가 지시할 때만 한다.
    - 다음 단위의 기능 명세처럼 문서만 다루는 작업은 별도 git worktree에서 현재 작업과 동시에 진행한다. 문서 작업은 빌드가 필요 없어 worktree 비용이 작다.
    - UE 코드 작업의 worktree 병렬화는 빌드 산출물과 DDC를 새로 만들어야 해서 쓰지 않는다.

## 수직 구현

입력, UI, Content, Actor lifecycle, 물리, collision, Navigation 또는 여러 대상의 공통화가 함께 바뀌면 대표 대상 하나의 사용자 흐름 전체를 먼저 완성한다.

```text
대표 시나리오 명세 → 설계 → 구현 → 코드 리뷰 → Editor 작업
→ 사용자 PIE 검증·플레이 승인 → 전체 확장 설계부터 동일 흐름 반복
```

- 일부 C++ 계층만 만드는 것은 수직 구현이 아니다.
- 사용자 승인 전에는 다른 설비·아이템·상태로 동작을 일반화하지 않는다.
- 단순 계산, 로그 또는 Content 비의존 내부 버그는 근거를 남기고 전체 수정 경로를 사용할 수 있다.
- 대표 시나리오와 전체 확장은 서로 다른 작업 ID와 작업 폴더를 쓴다.

## 컨텍스트와 인계

- 마스터는 현재 대화의 이전 결정과 진행 상황을 유지하고 새 하위 에이전트에 작업 폴더 경로, 필요한 컨텍스트와 문서를 전달한다.
- 이미 호출된 하위 에이전트는 이후 마스터 대화를 자동으로 동기화하지 않는다.
- 같은 하위 에이전트를 재개하면 그 에이전트의 이전 작업 컨텍스트를 이어서 사용한다. 실행 도구가 재개를 지원하지 않으면 작업 폴더와 `CONTEXT.md`로 새 에이전트에 인계한다.
- 중요한 결정은 정기 결과물과 정본 문서에 반영하며, 새 요구사항은 후속 메시지나 갱신 문서로 전달한다.

## 단계 인계 계약

각 에이전트의 완료 보고와 다음 단계 프롬프트에는 최소한 다음을 포함한다.

- 작업 ID와 작업 폴더, 현재 단계와 관련 시나리오 ID
- 읽은 정본과 입력 결과물
- 수행한 변경 또는 조사 범위
- 확정한 내용과 다음 역할이 결정해야 할 내용
- 검증한 항목, 실패와 미검증 항목
- 사용자 소유 변경, dirty package와 저장 상태
- 결론: 완료, 재작업, 상위 단계 복귀 또는 사용자 결정 필요
- 버그 수정 작업이면 확정 원인, 유입 단계와 원래 검출했어야 할 단계
- 다음 단계 프롬프트: 읽을 시스템 문서 목록, 시나리오 ID 구간과 단계 시작 커밋
- 완료 보고: 결론과 파일 경로 중심 20줄 이내, 구현·Editor 단계는 시나리오 ID별 PIE 관찰 항목 포함

마스터는 말로만 전달된 중요한 결정을 다음 단계에 넘기기 전에 소유 결과물에 반영한다. 새 에이전트에는 전체 대화를 무조건 복제하기보다 현재 정본, 작업 폴더의 결과물과 필요한 결정 요약을 전달한다.

## 기존 에이전트와 새 에이전트 선택

기본 기준은 `연속성이 필요하면 기존 에이전트, 독립성이 필요하면 새 에이전트`다.

### 기존 에이전트 재개

- 동일 작업·역할의 미완료 작업, 자신이 만든 구현의 후속 수정
- 직전 결과 질문, 리뷰 지적 반영 또는 기존 판단 과정이 필요한 원인 분석
- 코드 리뷰 실패 재작업 후의 재검증(원래 리뷰어)

### 새 에이전트 생성

- 독립된 신규 작업·다른 역할, 첫 코드 리뷰, 사용자 PIE 버그 수정 후의 코드 리뷰
- 요구사항·설계의 근본 변경, 과도한 컨텍스트 또는 잘못된 가정 반복
- 복수 대안을 독립적으로 비교하거나 병렬 처리하는 경우

구현 후속 수정은 기존 구현 에이전트가 맡고, 재승인은 별도의 리뷰 에이전트가 맡는 것을 기본으로 한다. Unreal Editor 역할 안에서 MCP·Python·화면 작업 모드를 오가는 것은 같은 에이전트의 수단 전환이며 새 에이전트 생성 사유가 아니다.

판단 순서는 다음과 같다.

```text
같은 작업·같은 책임인가?
├─ 아니오: 새 에이전트
└─ 예
   ├─ 독립 검토가 필요한가: 새 에이전트
   ├─ 요구사항이 근본적으로 바뀌었는가: 새 에이전트
   ├─ 기존 컨텍스트가 과도하거나 반복 오판하는가: 새 에이전트
   └─ 나머지: 기존 에이전트 재개
```

기존 에이전트의 컨텍스트가 필요하지만 독립 검토도 필요하면 담당 에이전트가 수정하고 별도 리뷰 에이전트가 검증한다.

## Unreal 실행 경계

- Editor 조사와 작업은 범용 Unreal Editor 역할 하나가 맡는다. MCP 전용 역할과 별도 Python 역할은 두지 않는다.
- 진입 모드는 둘이다. 읽기 전용 조사는 기능 명세·아키텍처의 exact 조사 요청이나 진단 요청으로, Editor 작업은 코드 리뷰 승인과 현재 작업 폴더의 `PROMPT_UNREAL.md`(재작업은 `PROMPT_UNREAL_R.md`)로 진입한다.
- 실행 수단(MCP, 공식 Editor Python API, 검토된 C++ Editor 보조 도구, headless commandlet)은 Editor 역할이 실제 capability를 확인해 고른다. 마스터는 수단을 지정하지 않으며, 승인 범위 안의 수단 전환마다 재승인을 받지 않는다. 작업별 명시 제한은 지킨다.
- Computer Use는 같은 역할의 화면 작업 모드이며 마지막 수단이다. MCP, Python, 기존 helper, commandlet 등 허용된 자동화 경로를 모두 시도하고, 화면 작업 없이 끝낼 수 있는 항목을 먼저 모두 마친 뒤에만 고려한다.
- 화면 작업 모드는 작업 직전에 사용자 승인을 받는다. 명세 승인 때의 사전 허용이나 이전 작업의 승인으로 대신하지 않는다.
  - Editor 역할은 화면 작업 후보를 대상 asset, 필요한 조작, 자동화 경로의 실패 근거, 예상 범위로 정리해 보고한다.
  - 마스터가 사용자에게 승인을 받으면 같은 Editor 에이전트를 재개해 승인된 항목만 화면 작업으로 처리한다. 승인되지 않은 항목은 `USER_UNREAL.md`에 기록한다.
  - native 실행 환경이 지원하지 않으면 승인과 관계없이 `USER_UNREAL.md`에 기록한다.
- MCP·Python 실패를 화면 조작 허용으로 확대하지 않는다.
- `.uasset`·`.umap`은 공식 Editor API와 검토된 도구로만 수정·저장한다. 셸·텍스트·바이너리 패치는 금지한다.
- Editor 역할은 Source, Config, Architecture 정본과 입력 프롬프트를 수정하지 않는다. 신규 C++ helper나 Config 변경이 필요하면 설계·구현 단계로 반환한다.
- 허용된 자동화로 완료할 수 없는 실제 Editor 작업만 한국어 `.md/USER_UNREAL.md`에 작업 ID, exact 대상, 확인한 경로·오류, 남은 조작과 재개 조건으로 기록한다.
- Editor 변경은 allowlist asset만 Compile, Data Validation, 개별 Save, 재로드하고 재로드로 확인된 상태만 관련 `.md/Unreal/*System.md`에 반영한다.
- Editor 역할의 검증은 재로드 readback까지다. PIE 시작·종료, PIE 입력과 플레이 시나리오 검증은 수행하지 않고, 완료 보고에 시나리오 ID별 PIE 관찰 항목을 남긴다.
- 세부 절차는 통합안의 `AGENT_UNREAL_EDITOR.md`, `UNREAL_MCP_CONNECTION.md`, `UNREAL_PYTHON_API.md`를 따르며 이 제안에 복제하지 않는다.

## 후속 문제 분류와 복귀

| 문제 유형 | 책임 단계 | 기본 처리 |
|---|---|---|
| 승인된 동작과 다른 코드 실행 | 구현 | 새 리뷰어가 진단해 `PROMPT_IMPLEMENTATION_R.md` 작성, 기존 구현 에이전트 수정 후 그 리뷰어가 재검증 |
| Blueprint·Level·StateTree·Widget 설정 오류 | Unreal Editor | Unreal Editor 읽기 전용 조사 후 마스터가 `PROMPT_UNREAL_R.md` 작성, Editor 재작업 후 사용자 PIE 재검증 |
| 상태 owner·좌표·lifecycle 구조 오류 | 아키텍처 | 재설계 후 구현부터 반복 |
| 문서대로 구현됐지만 사용자 기대와 다름 | 기능 명세 | 동작 계약을 다시 승인 |
| 코드와 Editor가 각각 맞지만 함께 실패 | 마스터 분류 | 필요하면 Editor 읽기 전용 조사로 양쪽 계약을 추적해 책임 단계로 반환 |
| 기존 범위 밖의 개선 요구 | 기능 명세 | 신규 작업으로 시작 |
| 에이전트 선택·단계·인계 실패 | 오케스트레이터 | 워크플로우 회고 대상으로 기록 |

### 복귀 원칙과 범위 최소화

- 코드 리뷰나 Editor 작업에서 상위 단계 결함이 드러나면, 이미 끝낸 코드·리뷰·Editor 작업의 비용과 관계없이 책임 단계로 복귀한다. 판단 기준은 이미 쓴 비용이 아니라 지금부터의 비용이다.
- 상위 단계 결함을 Blueprint graph, asset 값이나 Level 배치로 우회하지 않는다. 우회는 C++ 계약, Architecture 정본과 실제 asset을 어긋나게 해 이후 설계와 사용자 PIE의 비용을 키운다.
- 마스터는 책임이 있는 가장 낮은 단계로 복귀시킨다.

| 판정 | 복귀 대상 |
|---|---|
| asset이 틀렸고 C++ 계약이 맞음 | 복귀 없음. Editor 단계 안에서 수정 |
| 계약은 맞고 구현이 틀림 | 구현 |
| 계약 자체가 실제 asset·Level·엔진 동작과 맞지 않음 | 아키텍처 |
| 사용자 동작을 다시 정해야 함 | 기능 명세 |

- 복귀한 단계는 영향받는 시나리오 ID와 asset만 다시 정한다. 결과물에 변경 범위를 적고, 이후 단계는 그 범위만 재구현·재리뷰한다. 재리뷰는 단계 시작 커밋 기준 diff로 수행한다.
- Editor 작업 중 상위 단계 결함이 드러나면 영향받는 asset의 변경만 저장하지 않고 멈춘다. 영향이 없는 allowlist 항목은 계속 진행해 저장·재로드까지 마치고, 복귀 후에는 남은 부분과 바뀐 부분만 처리한다.
- 마스터는 복귀 대상, 변경 범위와 유지되는 완료 범위를 `CONTEXT.md`에 적는다.

## 즉시 피드백 형식

마스터는 담당 에이전트에 단순 재작업 명령 대신 다음 내용을 전달한다.

- 버그 리포트 경로(있으면)와 관련 작업·시나리오 ID
- 승인된 계약과 실제 관찰 결과
- 로그, PIE, 코드 또는 asset 근거
- 확정된 책임 단계와 근본 원인, 미확정이면 조사 범위
- 요청하는 수정 결과와 금지할 임시 우회
- 회귀 검증 조건과 워크플로우 복귀 지점

찐빠를 낸 에이전트는 사건과 원인을 보고할 수 있지만 자기 판단만으로 공통 지침을 추가하지 않는다.

예시 피드백 패킷은 다음과 같다.

```text
[버그 리포트 경로 / 작업 ID / 시나리오 ID]
[승인된 계약]
[실제 관찰과 재현 조건]
[로그·PIE·코드·asset 근거]
[유입 단계 / 검출 실패 단계]
[확정 원인 또는 추가 조사 범위]
[요청 수정 / 금지할 임시 우회]
[회귀 검증 / 복귀 지점]
```

## 기록 계층 제안

```text
.md/BugReports/<보고일>_<요약>.md        (현행 유지)
.md/FEEDBACK_BACKLOG.md                  (모든 역할의 Feedback 한 파일)
```

- `BugReports/*.md`: 사용자가 관찰한 개별 버그의 현상 기록. 현재 형식과 위치를 유지한다.
- `Work/<작업 ID>/`: 버그 수정을 포함한 진행 중 작업의 단계 결과물. 원인과 수정 내용은 해당 작업 결과물과 커밋에 남는다.
- `FEEDBACK_BACKLOG.md`: 에이전트별 파일로 나누지 않는 한 파일이다. 두 부분으로 나눈다.
  - 일반화 항목: 여러 사건에서 일반화된 경험적 교훈. 역할 태그를 붙이며 에이전트가 적용하는 대상이다.
  - 상위 단계 복귀 기록: 코드 리뷰나 Editor 작업이 기능 명세·아키텍처 단계로 재작업을 돌려보낸 사건의 짧은 원본 기록. 에이전트가 적용하지 않으며 회고 입력으로만 쓴다.
- `AGENT_*.md`: 권한, 절대 금지, 승인 관문과 결과물 소유권 같은 안정적인 역할 계약
- `Architecture/*`와 `Unreal/*`: 버그 이력이 아니라 해결 후 확정된 현재 구조
- `USER_UNREAL.md`: 현재 남은 실제 Editor 수동 작업만 유지

각 에이전트는 `FEEDBACK_BACKLOG.md`에서 자기 역할 태그가 붙은 항목만 기본 대상으로 삼고, 버그 리포트는 관련 진단이나 회고 때만 조회한다.

역할 태그는 `ORCHESTRATOR`, `FEATURE_SPEC`, `ARCHITECTURE`, `IMPLEMENTATION`, `REVIEW`, `UNREAL_EDITOR`다. Computer Use 화면 작업 모드의 교훈은 `UNREAL_EDITOR` 태그를 쓴다.

## 버그 기록

- 현재 `BugReports/` 방식을 그대로 쓴다. 파일 하나에 버그 하나이며, 보고일, 발견 경로, 상태, 현상, 재현 조건, 기대 동작, 실제 동작, 영향 범위, 재현 빈도와 미확인 항목을 적는다.
- 버그 리포트는 사용자가 관찰한 현상을 기록한다. 상세 원인 분석은 버그 수정 작업 폴더의 결과물에 두고, 일반화 판단은 요청된 회고와 Feedback 항목에 둔다.
- 버그 수정 작업은 리포트 파일명에서 작업 ID를 만든다.
- 사용자 PIE 재검증을 통과하면 마스터가 리포트의 상태 줄을 갱신하고, 기존 형식 맨 아래에 다음 `수정 결과` 네 줄만 덧붙인다. 내용은 버그 수정 작업의 완료 보고에서 옮기며 새로 분석하지 않는다.

```markdown
## 수정 결과

- 원인: <확정 원인 한 줄>
- 유입 단계: <결함이 들어온 단계와 작업·커밋>
- 검출 실패 단계: <원래 잡았어야 할 단계와 놓친 이유 한 줄>
- 수정 커밋: `<커밋 해시>`
```

- 이 네 줄이 회고의 기본 입력이다. 작업 폴더는 제거되므로, 회고는 네 줄로 판단이 부족할 때만 수정 커밋의 Git 이력을 조회한다.
- 버그 기록은 작업 지침이 아니다. 일반 에이전트는 전체 버그 목록을 기본으로 읽지 않으며 마스터나 회고 에이전트가 관련 버그만 조회한다.

## 역할별 피드백 형식

각 일반화 항목에는 다음을 기록한다.

- Feedback ID와 상태: `Experimental`, `Active`, `Retired`
- 역할 태그(하나 이상)와 시스템 태그
- 재발 패턴과 적용 범위
- 유입 단계와 원래 검출했어야 할 게이트
- 잘못된 판단이 만드는 위험
- 권장 행동과 검증 방법
- 근거: 버그 리포트 경로와 수정 커밋, 상위 단계 복귀 기록 ID, 둘 다 없으면 작업 ID와 커밋
- 적용하지 않을 조건

### 상위 단계 복귀 기록 형식

코드 리뷰 또는 Editor 작업 결과 기능 명세나 아키텍처 단계로 재작업이 결정되면, 마스터가 복귀 실행 전에 `FEEDBACK_BACKLOG.md`의 복귀 기록 부분에 다음을 남긴다. 내용은 리뷰 결과물이나 Editor 작업 보고에서 옮기며 새로 분석하지 않는다. Editor 도구의 기능 한계(MCP·Python 미지원 등)는 설계 결함이 아니므로 복귀 기록 대상이 아니다.

```markdown
### RET-<번호> <한 줄 요약>

- 일자·작업 ID: <날짜>, `<작업 ID>`
- 발견 단계: 코드 리뷰 | Editor 작업
- 복귀 대상: 기능 명세 | 아키텍처 (루프 한도 초과 복귀면 함께 표시)
- 문제: <드러난 상위 단계 결함 한 줄>
- 놓친 이유: <해당 단계에서 왜 정하지 못했거나 잘못 정했는지 한 줄>
- 검출 실패 단계: 코드 리뷰 | Editor 사전 조사 미요청 | 없음(Editor에서만 확인 가능) — 발견 단계가 Editor 작업일 때만
- 근거: <리뷰 결과물 또는 Editor 작업 보고 경로와 해당 시점 커밋>
```

Editor 작업에서 발견된 복귀의 검출 실패 단계는 마스터가 다음 기준으로 판정한다.

| 드러난 사실이 코드 리뷰 시점에 어디 있었나 | 검출 실패 단계 |
|---|---|
| `Unreal/*System.md` 또는 사전 조사 보고에 이미 있었음 | 코드 리뷰. 정본과 대조했으면 잡을 수 있었다 |
| 문서에 없었고 실제 asset을 봐야만 알 수 있었음 | Editor 사전 조사 미요청. 기능 명세나 아키텍처가 조사를 요청했어야 했다 |
| Editor에서만 일어나는 엔진 경로(재인스턴싱, 저장·재로드 등) | 해당 경로를 점검 항목으로 볼 수 있었으면 코드 리뷰, 아니면 없음 |

- 복귀 기록은 작업 지침이 아니다. 일반화나 상태 부여 없이 쌓아 두고, 사용자가 요청한 회고에서만 일반화 후보로 검토한다.
- 회고에서 검토를 마친 복귀 기록은 일반화 항목의 근거로 연결한 뒤 제거한다.
- 사용자 PIE에서 발견된 문제는 복귀 기록이 아니라 버그 리포트로 기록한다.

Feedback은 경험적 지침이며 `AGENT_*.md`와 충돌하면 역할 계약을 우선한다. 안전, 권한, 필수 승인과 결과물 소유권은 Feedback이 아니라 `AGENT_*.md`에 둔다.

## Feedback 로딩과 정리

- `FEEDBACK_BACKLOG.md` 첫머리에 일반화 항목의 Feedback ID, 역할 태그, 시스템 태그, 상태만 담은 색인 표를 두고, 에이전트는 색인으로 해당 항목만 찾아 읽는다. 상위 단계 복귀 기록 부분은 읽지 않는다.
- 전문 에이전트는 자기 역할과 현재 시스템에 관련된 `Active` 항목만 기본 적용한다.
- `Experimental` 항목은 마스터가 현재 작업의 검증 대상으로 명시했을 때 적용한다.
- `Retired` 항목은 일반 작업에서 읽지 않고 제거 또는 기록 보관 대상으로 처리한다.
- 같은 원인의 Feedback은 병합하고 특정 asset 이름·당시 좌표·임시 수치는 버그 리포트나 작업 결과물에만 둔다.
- 파일은 하나로 유지한다. 커지면 `Retired` 항목과 `AGENT_*.md`로 승격된 항목을 제거하고 같은 원인을 병합해 현재 유효한 판단만 남긴다.
- Feedback을 적용하지 않는 편이 맞으면 에이전트가 적용 제외 조건과 근거를 완료 보고에 남긴다.

## 일반화와 승격 책임

피드백 일반화, `FEEDBACK_BACKLOG.md` 등록·상태 변경과 `AGENT_*.md` 승격은 사용자가 요청할 때만 수행한다. 마스터와 전문 에이전트는 작업 완료, 버그 수정이나 반복 실패를 이유로 이를 자동 실행하지 않는다. 상위 단계 복귀 기록은 일반화가 아닌 원본 기록이므로 마스터가 평소에 남긴다.

```text
[평소] 담당 에이전트가 완료 보고에 원인과 유입 단계를 기록하고, 마스터가 버그 리포트에 수정 결과 네 줄을 덧붙임
[평소] 코드 리뷰나 Editor 작업이 기능 명세·아키텍처로 복귀시키면 마스터가 FEEDBACK_BACKLOG.md에 복귀 기록을 남김
[사용자 요청] 회고 에이전트가 지난 회고 기준점 이후의 버그 리포트 수정 결과와 복귀 기록에서 반복 패턴과 일반화 후보 분석
→ 마스터가 중복·충돌·과적합과 비용을 심사
→ 사용자에게 후보 보고, 필요한 경우 사용자 승인
→ 승인된 항목만 회고를 요청받은 세션이 Feedback 또는 AGENT 문서에 반영(QNA Q8)
```

- 회고 에이전트는 후보를 제안하며 단독으로 확정하지 않는다.
- 승인된 반영은 회고나 정책 변경을 사용자가 요청한 그 세션이 직접 한다. 워커 에이전트에는 `FEEDBACK_BACKLOG.md` 일반화 항목과 `AGENT_*.md`의 수정 권한을 주지 않는다. 문서 크기·중복 규칙은 그 세션이 `AGENT_WORKFLOW.md`의 문서 크기 정책으로 확인한다.
- `FEEDBACK_BACKLOG.md` 첫머리에 마지막 회고 기준점(날짜와 커밋)을 두고, 다음 회고는 그 이후 이력만 읽는다.
- 요청된 회고 안에서 기존 역할의 검증 항목 명확화와 저위험 Feedback은 마스터가 승인하고 보고할 수 있다.
- 새 단계, 새 결과물, 승인 관문, 권한 변경, 역할 재분배와 프로젝트 전체 비용 증가는 사용자 승인을 받는다.
- 안전 또는 항상 지켜야 할 불변 계약만 Feedback에서 `AGENT_*.md`로 승격한다.

사용자 승인이 필요한 변경은 새 단계·결과물·승인 관문, 에이전트 권한, 역할 책임, Unreal Editor 실행 수단과 화면 작업 모드의 경계 또는 프로젝트 전체 작업 비용을 바꾸는 경우다. 기존 계약을 바꾸지 않는 표현 명확화와 저위험 Feedback 정리는 마스터가 처리하고 결과를 보고할 수 있다.

## 워크플로우 개선 사이클

```text
[작업 흐름 안에서 자동]
사용자 PIE·플레이에서 버그·의도 불일치 발견
→ BugReports/에 현상과 재현 조건 기록
→ 진행 중 작업이면 그 작업 폴더, 완료된 작업이면 새 BUG- 작업 폴더
→ 새 리뷰어가 원인 진단 (Editor 설정 문제는 Editor 읽기 전용 조사)
→ 구현 문제: 리뷰어가 PROMPT_IMPLEMENTATION_R.md → 구현 수정 → 같은 리뷰어 재검증
  Editor 설정 문제: 마스터가 PROMPT_UNREAL_R.md → Editor 재작업
  설계·명세 문제: 아키텍처 또는 기능 명세로 복귀
→ 필요하면 Editor 작업
→ 사용자 PIE 재검증
→ 수정 커밋
→ 버그 리포트 상태 갱신과 수정 결과 네 줄 추가, 작업 폴더 제거, 커밋

[작업 흐름 안에서 자동, 코드 리뷰·Editor 작업의 상위 단계 복귀]
코드 리뷰나 Editor 작업이 기능 명세·아키텍처 결함으로 판정
→ 마스터가 FEEDBACK_BACKLOG.md에 복귀 기록 작성
→ 범위 최소화 원칙에 따라 해당 단계로 복귀해 영향 범위만 재작업

[사용자 요청 시]
→ 회고: 기준점 이후 버그 리포트 수정 결과와 상위 단계 복귀 기록의 반복성·일반성 평가
→ 승인된 항목을 FEEDBACK_BACKLOG.md에 역할 태그를 붙여 Experimental 등록
→ 이후 회고 요청 때 유효성 확인
→ Active 유지, AGENT 계약 승격 또는 Retired 처리
```

다음 중 두 개 이상이면 일반화 후보로 본다.

1. 다른 기능에서도 재발할 가능성이 있다.
2. 특정 asset이나 수치가 아닌 일반 계약으로 표현할 수 있다.
3. 항상 확인하면 재작업 비용을 줄일 수 있다.
4. 기존 리뷰나 테스트로 검출할 수 있었던 문제다.

단일 사건의 구체적인 Actor 이름, 당시 좌표와 임시 해결값은 Feedback이나 `AGENT_*.md`로 승격하지 않는다.

## 마스터 세션과 일반 세션

- 마스터 세션은 사용자가 오케스트레이션 Skill을 명시적으로 호출해 시작한다. 예: `/orchestrate`, `/orchestrate SERVICE-U4 이어서`.
- Skill은 모델이 스스로 호출하지 못하게 설정하고 사용자 호출로만 시작한다. `AGENTS.md`에도 세션을 자동으로 마스터로 만드는 문구를 두지 않는다.
- 사용자는 작업마다 새 세션을 열고 Skill로 마스터를 시작한다. 마스터는 작업 완료 보고 끝에 `다음 작업은 새 세션에서 시작` 안내 한 줄을 붙인다.
- Skill을 호출하지 않은 일반 세션은 마스터가 아니다. 독립 모델링, 다음 작업의 기능 명세 논의, 단일 질문처럼 사용자가 직접 한 역할을 지정해 쓰며, 그 세션은 `AGENTS.md`와 해당 역할 지침을 따른다.
- 일반 세션이 작업 폴더의 단계 결과물을 만들면 결과물 소유권과 첫머리 형식을 지키고 `CONTEXT.md`의 재개 지점만 갱신한다. 다음 단계를 자동으로 호출하지 않는다. 이후 마스터 세션이 `CONTEXT.md`와 결과물 첫머리로 이어받는다.
- 일반 세션에서 확정한 사용자 결정(예: 기능 명세 QNA 답변)은 대화에만 두지 않고 해당 작업 폴더의 결과물에 기록한다.

### 기능 명세 Skill

기능 명세만 진행하는 일반 세션의 진입점으로 사용자 호출 전용 기능 명세 Skill(예: `/feature-spec`)을 둔다.

- 호출 형식: `/feature-spec <새 기능 설명>` 또는 `/feature-spec <작업 ID> 이어서`.
- Skill은 `AGENT_WORKFLOW.md`와 `AGENT_FEATURE_SPEC.md`를 읽히는 일만 하며 규칙을 복제하지 않는다. 기능 명세의 형식과 절차는 두 지침서가 정본이다.
- 새 기능이면 작업 ID를 정하고 `Work/<작업 ID>/`와 `CONTEXT.md`를 만든다. 이어서 하는 작업이면 `CONTEXT.md`와 결과물 첫머리로 현재 상태를 확인한다.
- 기능 명세 단계의 결과물만 작성한다. 필요하면 Unreal Editor 읽기 전용 조사를 요청할 수 있다. 아키텍처 이후 단계는 호출하지 않는다.
- 명세 승인을 받으면 승인 일자와 사전 허용을 `CONTEXT.md`에 적고, 결과물 첫머리를 `완료`로 바꾼 뒤 `/orchestrate <작업 ID> 이어서`로 마스터 세션을 시작하라고 안내하고 끝낸다.
- 이 Skill은 세션을 마스터로 만들지 않는다. 모델이 스스로 호출하지 못하게 설정한다.
- 세션 모델은 사용자가 세션을 열 때 고르며, 기능 명세 역할의 요구 수준에 맞춰 Opus 5.5 high를 권장한다.

## 오케스트레이션 Skill

마스터 세션의 진입점으로 `SKILL.md`를 만든다. Skill은 현재 단계 판정, 호출·재개, 승인 관문과 복귀만 담당한다. 모델·추론 설정은 Skill이 아니라 역할별 정의 파일과 도구 설정이 소유한다. 프로젝트 규칙을 복제하지 않은 채 `AGENTS.md`, `AGENT_WORKFLOW.md`와 역할별 지침을 읽는다. 프로젝트 문서가 정본이며 Skill은 실행기다.

## 채택 시 필요한 후속 작업

1. `UnrealEditorWorkflowDraft/` 통합안을 먼저 채택해 `AGENT_UNREAL_MCP.md`와 `AGENT_UNREAL_PYTHON.md`를 범용 Unreal Editor 역할로 교체한다.
2. 마스터 오케스트레이터의 역할과 자동 전환 규칙을 `AGENT_ORCHESTRATOR.md`로 확정하고, 사용자 호출 전용 오케스트레이션 Skill을 진입점으로 만든다. 일반 세션용 기능 명세 Skill도 사용자 호출 전용으로 함께 만든다. `AGENTS.md`에는 마스터 지침의 위치만 라우팅하고 세션을 자동으로 마스터로 만드는 문구는 두지 않는다.
3. 작업 ID, 작업 폴더와 결과물 첫머리 형식을 `AGENT_WORKFLOW.md`의 정기 결과물·소유권에 반영하고, 역할 문서의 `.md/PROMPT_*.md` 경로를 작업 폴더 기준으로 바꾼다.
4. 진행 중인 결과물을 이관한다. 루트의 `PROMPT_*.md`·`QNA_*.md`와 `NextWork/`를 작업별 폴더로 옮기고 각 소유 단계가 첫머리를 단다.
5. Feedback 정책을 확정하고 `FEEDBACK_BACKLOG.md`를 일반화 항목과 상위 단계 복귀 기록의 두 부분 형식으로 정리한다. 기존 항목은 역할 태그·상태를 붙인 일반화 항목으로 바꾸고, 사건 사실은 필요하면 `BugReports/` 형식으로 옮긴다. 첫머리의 `작업 중 이 문서를 지시로 따르지 않는다` 문구는 `Active` 항목 적용 규칙으로 바꾼다.
6. 회고 권한과 승인 기준을 정하고 `AGENT_WORKFLOW.md`에는 라우팅과 필수 경계만 반영한다.
7. 역할별 요구 수준을 실행 도구별 설정에 연결한다. Claude 워커 역할마다 `.claude/agents/<역할>.md`(`model`, `effort`, `tools`)를 만들고, Codex 워커는 `~/.codex/config.toml` 값을 확인한다. Claude 정의 파일은 기능 명세, 아키텍처, 코드 리뷰, Unreal Editor, 회고(`opus`, `high`)와 구현 대체(`claude-sonnet-5-5`, `medium`)의 여섯 역할이고, C++ 구현의 기본은 Codex 워커다.
8. 통합 리뷰 단계를 제거한다. `AGENT_INTEGRATION_REVIEW.md`를 정본 목록에서 빼고, 통합안 Editor 작업 순서의 PIE·입력 검증 단계와 통합 리뷰 연결 항목을 정리한다. Editor 완료 보고 `PROMPT_INTEGRATION_REVIEW.md`는 Editor 작업 결과 보고로 이름과 역할을 정리하고, 사용자 PIE 체크리스트는 마스터의 `PIE_CHECKLIST.md`로 분리한다.
