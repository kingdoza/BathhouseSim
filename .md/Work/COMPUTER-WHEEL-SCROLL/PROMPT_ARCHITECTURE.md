# 기능 명세 — COMPUTER-WHEEL-SCROLL 컴퓨터 화면 스크롤 영역 마우스 휠 스크롤

- 작업 ID: `COMPUTER-WHEEL-SCROLL`
- 단계: 기능 명세
- 상태: 진행

사용자 답변 전 초안이다. 미확정 선택은 [QNA_FEATURE_SPEC.md](QNA_FEATURE_SPEC.md)의 Q1~Q4이고, 아래 본문은 모두 추천안 기준으로 썼다. 질문 없이 적용하는 전제는 같은 문서의 P1~P12다.

## 1. 목적과 범위

사용자 요청 원문: "인게임컴퓨터에서 스크롤영역위에 마우스있을때는 플레이어 마우스스크롤로도 스크롤 되게하기"

플레이어 행동과 결과로 다시 쓰면 다음과 같다.

- 플레이어가 컴퓨터에 포커스인해 커서가 보이는 상태에서, 커서를 화면의 스크롤 영역(예: 상점 상품 목록) 위에 두고 마우스 휠을 굴리면 그 영역의 내용이 휠 방향으로 스크롤된다.
- 커서가 스크롤 영역 위에 없거나 컴퓨터를 쓰지 않을 때는 휠이 화면을 스크롤하지 않는다.

범위(Q1 A 기준): 컴퓨터 화면(관리·상점 탭)의 모든 세로 스크롤 영역. 앞으로 컴퓨터 화면에 추가되는 스크롤 영역도 같은 규칙을 따른다.

## 2. 현재 동작과 목표 동작

### 2.1 현재 컴퓨터 화면의 스크롤 영역(조사 필요)

| 탭 | 영역 | 근거 | 현재 휠 동작 |
|---|---|---|---|
| 상점 | 상품 목록 | Architecture `ShopSystem.md` UI 절 `ProductScroll`(필수 연결), 승인된 SHOP-032 "넘치면 목록만 세로 스크롤" | 스크롤되지 않음(추정) |
| 상점 | 장바구니 목록 | `WBP_ShopScreen.uasset` 안의 이름 문자열 `CartScroll`(Content 단서, 미확정) | 스크롤되지 않음(추정) |
| 상점 | 주문 목록 | `WBP_ShopScreen.uasset` 안의 이름 문자열 `OrderScroll`(Content 단서, 미확정) | 스크롤되지 않음(추정) |
| 관리 | 욕탕 상세 영역(순환도·목표 수온 슬라이더 포함) | Unreal `InteractionUISystem.md` "Detail은 `ScrollBox` 안에 있다", `WBP_BathWaterDetail.uasset` 문자열 `DetailScroll` | 스크롤되지 않음(추정) |

- 위 Content 단서는 asset 파일의 이름 문자열 검색 결과일 뿐이다. 영역 목록, 중첩 여부, 방향은 6절 Editor 사전 조사로 확정한다.
- Unreal 정본은 `BP_BathhouseComputer.ScreenWidget.WidgetClass`를 관리 화면 WBP로 기록하지만, Architecture `ShopSystem.md`는 탭 root WBP로 교체했다고 적는다. 실제 값은 조사 대상이다.

### 2.2 현재 휠 입력 경로(Source 근거, PIE 미확인)

- 컴퓨터 포커스 중 화면은 실제 마우스 입력을 직접 받지 않고, 플레이어 쪽 가상 포인터가 LMB 누름·뗌만 화면에 전달한다. 휠은 화면에 전달되지 않는다.
- 플레이어 입력에는 마우스 휠이 배치 중 설비 회전(Yaw)에 매핑돼 있다(Architecture `PlacementSystem.md`·`CharacterSystem.md`. `IMC_FirstPerson.uasset`에 `MouseWheelAxis`와 `IA_PlacementRotate` 문자열 존재, 실제 mapping은 조사 대상).
- 컴퓨터 포커스 중에는 Character가 설비 회전 입력을 차단한다(Architecture `CharacterSystem.md` "computer session이 capture 중이면 … 휠을 차단한다"). 컴퓨터는 빈손일 때만 쓸 수 있어 배치 중일 수도 없다.
- 따라서 현재 컴퓨터 포커스 중 휠은 화면의 어느 영역도 스크롤하지 않고, 다른 동작도 하지 않는 것으로 판단한다. 영역이 넘칠 때 플레이어는 스크롤바를 LMB로 끌어야만 내용을 볼 수 있다(스크롤바 표시 여부는 조사 대상).

### 2.3 목표 동작

- 컴퓨터 포커스가 조작 가능 상태일 때 커서 아래 스크롤 영역이 휠로 스크롤된다.
- 스크롤 영역 밖(화면 안의 다른 곳, 화면 바깥의 월드)에서는 휠이 아무 일도 하지 않는다(Q2 A).
- 컴퓨터를 쓰지 않을 때의 휠 동작(배치 중 설비 회전)은 그대로다.

### 2.4 기존 정본과 달라지는 점

- Architecture `ComputerSystem.md` Out Of Scope의 "범용 desktop, app window, keyboard text input와 scroll"에서 컴퓨터 화면 스크롤 영역의 휠 스크롤이 범위 안으로 들어온다. 범용 desktop·text input은 여전히 범위 밖이다.
- Architecture `CharacterSystem.md`의 "컴퓨터 사용 중 휠 차단"은 "컴퓨터 사용 중 휠은 화면 스크롤에만 쓰이고 그 밖의 동작(설비 회전 등)에는 닿지 않는다"로 바뀐다. 사용자가 관찰하는 차단 결과(설비·시점 변화 없음)는 유지된다.

## 4. 동작 계약

### 4.1 시작 조건과 입력

- 컴퓨터 포커스 진입이 끝나 커서가 보이고 화면 클릭이 가능한 상태(P1).
- 커서가 컴퓨터 화면 위의 스크롤 영역 위에 있다. 영역 안의 카드·버튼·문구·슬라이더 위도 영역 위다(P5, Q3 A).
- 플레이어가 마우스 휠을 위·아래로 굴린다. 진입 직후 클릭이 필요 없고, LMB 상태와 무관하다(P6).

### 4.2 즉시 피드백과 완료 시점

- 휠 한 칸(또는 트랙패드의 휠 양)이 입력된 그 프레임에 영역 내용이 이동한다. 애니메이션이나 지연 없이 바로 반영되며, 그것이 완료 시점이다(P3).
- 휠 아래 = 아래쪽 내용이 올라와 보임, 휠 위 = 반대(P2).
- 새 안내 문구·커서 모양·강조는 없다(P11). 스크롤바가 표시되는 영역이면 스크롤바 위치가 함께 움직인다.

### 4.3 경계 결과

- 끝에 닿으면 멈추고 튕김이 없으며 반대 방향은 즉시 움직인다. 내용이 영역보다 작으면 아무 일도 없다(P3).
- 중첩 영역은 커서 아래 가장 안쪽 영역이 우선이고, 그 방향 끝이면 바깥 영역이 이어받는다. 한 칸이 두 영역을 동시에 움직이지 않는다(P4).
- 휠은 클릭·담기·탭 전환·수량 변경·욕탕 설정 변경을 일으키지 않는다(P5, Q3 A).

### 4.4 성공 후 상태

- 스크롤은 표시 위치만 바꾼다. 장바구니·잔액·주문·욕탕 설정·용량은 변하지 않는다.
- 스크롤된 위치에서 LMB 클릭은 그때 커서 아래에 보이는 항목에 적용된다.
- 스크롤 위치는 포커스아웃 뒤 재진입, 탭 전환 뒤 복귀에도 유지된다(P9).

### 4.5 반드시 유지할 기존 기능

- 컴퓨터 진입·이탈: 빈손 E 진입, E·ESC 이탈, 고정 이탈 위치, 진입마다 커서 화면 중앙, 시점 blend.
- 컴퓨터 화면 LMB 클릭(버튼·슬라이더·탭)과 포커스아웃 시 눌린 포인터 해제.
- 컴퓨터 사용 중 이동·시점·점프·sprint·F·G·Q·LCtrl 차단과 world interaction prompt 억제.
- 컴퓨터를 쓰지 않을 때 배치 중 휠 설비 회전(P8).
- 포커스아웃이 화면을 파괴하지 않고 마지막 상태를 유지하는 계약.
- 상점 레이아웃: 상품이 넘치면 상품 목록만 스크롤되고 장바구니·주문 패널은 항상 보인다(SHOP-032).

### 4.6 사용자가 조정하는 값

| 값 | 기본 | 단위·좌표 기준 | 조정 |
|---|---|---|---|
| 휠 한 칸당 이동량 | 각 영역의 현재 Content 설정(조사로 확인) | 컴퓨터 화면 px, 화면 그리기 크기 1024×576 기준 | 스크롤 영역별 Editor 조정, PIE 후 변경 |

### 4.7 하지 않는 동작과 범위 밖

- 스크롤 영역 밖 휠로 다른 영역 스크롤(Q2 A), 슬라이더 값 휠 조정(Q3 A).
- 가로 전용 스크롤 영역(P12), 키보드(방향키·PageUp/Down)·드래그 관성 스크롤, 스크롤 위치 저장(P9).
- 휠용 새 HUD·안내(P11), 목록 내용 변경 시 스크롤 위치 정책 변경(P10).
- 세신 포커스 등 컴퓨터가 아닌 다른 포커스 모드의 휠.
- 관련 BUG 작업의 현상 1(슬라이더 한계 초과)·현상 2(클릭 없이 E 포커스아웃 실패) 수정(7절).

- CWS-019는 6절 조사에서 현재 화면에 중첩 영역이 없으면 PIE 대상이 아니며 설계·자동화 기준으로만 쓴다.
- 수치 감각(한 칸당 이동량)은 PIE 뒤 Editor 조정값이며 수용 실패 사유가 아니다. 너무 느리거나 빠르면 영역과 원하는 감각을 알려 주면 된다.

## 7. 관련 작업과의 경계

관련 작업 `BUG-2026-09-25_bath_water_slider_overrun_and_computer_focus_out`(아키텍처 대기):

- 현상 2(진입 뒤 클릭 없이 E로 이탈되지 않음)는 이 작업 범위가 아니다. 이 작업은 그 버그를 고치지도, 고쳐졌다고 가정하지도 않는다.
- 두 작업은 같은 컴퓨터 입력 경로(포인터·키보드 focus 라우팅)를 다룰 수 있다. 이 작업의 계약은 그 버그의 기대 동작과 충돌하지 않는다.
  - 휠 스크롤은 화면 클릭을 전제로 하지 않는다(CWS-003). 버그 수정 기대("클릭 없이 E로 이탈")와 같은 방향이다.
  - 휠 사용은 E·ESC 결과를 바꾸지 않는다(CWS-016). 버그가 남아 있는 동안 CWS-016의 판정 기준은 "휠을 쓰지 않았을 때와 같은 결과"이며, 클릭 없는 E 이탈 실패 자체는 이 작업의 실패가 아니다. 버그가 먼저 고쳐졌다면 휠을 쓴 뒤에도 클릭 없이 E·ESC로 이탈돼야 한다.
- 현상 1(슬라이더 한계 초과)과 겹치지 않도록 휠은 슬라이더 값을 바꾸지 않는다(Q3 A).
- 두 작업의 구현 순서와 공통 경로 변경 조율은 아키텍처 단계에 맡긴다.

## 8. 실패·취소·복구 계약

- 스크롤은 표시 위치만 바꾸므로 되돌릴 domain 상태가 없다. 어떤 경우에도 장바구니·잔액·주문·욕탕 설정이 휠로 바뀌지 않는다.
- 휠을 굴리는 중 E·ESC로 이탈하거나 진입·이탈 전환 중 휠을 굴려도 이탈은 평소대로 끝나고, 이탈 뒤 휠은 컴퓨터를 쓰지 않을 때의 동작으로 돌아간다(CWS-013, 017, 018).
- 컴퓨터 또는 플레이어가 비정상 종료돼 컴퓨터 사용이 강제로 끝나도 휠이 화면이나 다른 동작에 묶인 채 남지 않는다. 다음 휠 입력은 컴퓨터를 쓰지 않을 때의 동작이다.
- 스크롤 영역의 내용이 비거나 영역이 화면에서 사라져도(탭 전환, 욕탕 선택 해제) 휠은 오류 없이 아무 일도 하지 않는다.

## 9. Editor authoring 기대

- 새 asset·새 화면은 필요하지 않을 것으로 기대한다. 실제 필요 여부는 아키텍처 단계가 판단한다.
- 한 칸당 이동량은 스크롤 영역별로 Editor에서 조정할 수 있어야 하며 단위는 컴퓨터 화면 px다(4.6).
- 상점 레이아웃 계약(SHOP-032)과 관리 화면 레이아웃은 바꾸지 않는다.

## 10. 수직 구현 판단

- 입력·UI 동작 추가이므로 기본은 수직 구현이지만, Q4 추천 A에 따라 한 작업에서 Q1 범위 전체를 구현하고 PIE에서 함께 확인한다. 대표 시나리오는 CWS-001(상점 상품 목록)이다.
- Q4 B를 고르면 이 작업은 CWS-001~006, 011~018, 020을 상품 목록 기준으로 완성하는 수직 구현이 되고, CWS-007~010·019는 별도 작업 ID의 확장으로 옮긴다.
