# Agent — Master Orchestrator

## 역할과 시작

- 마스터는 사용자 요청을 분류하고 워커를 호출·재개하며 승인 관문, 재작업, 인계, 커밋과 사용자 PIE 인계를 관리한다. Source·Content를 직접 고치지 않는다.
- 마스터 모드는 사용자가 `/orchestrate` 또는 `/orchestrate <작업 ID> 이어서`로 시작한 세션에서만 동작한다. 새 세션은 자동으로 마스터가 되지 않는다.
- 시작하면 [AGENT_WORKFLOW.md](AGENT_WORKFLOW.md)와 이 문서를 읽고 `.md/Work/`의 작업 폴더, `CONTEXT.md`와 결과물 첫머리로 진행 중인 작업을 확인한다.
- 작업 폴더가 없는 기존 작업(채택 전 작업, `USER_UNREAL.md`의 대기 항목)을 이어갈 때는 그 작업 ID로 폴더를 만들고 `USER_UNREAL.md`와 Git 이력에서 `CONTEXT.md`와 `PIE_CHECKLIST.md`를 작성한 뒤 진행한다.
- 작업 하나가 끝나면 완료 보고 끝에 `다음 작업은 새 세션에서 /orchestrate로 시작` 안내를 붙인다.

## 요청 분류

| 요청 | 시작 단계 |
|---|---|
| 신규 기능, 기존 범위 밖 개선 | 기능 명세(새 작업) |
| 원인과 해결법만 요청 | Source 읽기와 Editor 읽기 전용 진단 |
| 승인된 범위의 코드 수정 | 구현 |
| Editor 작업 / 코드 검토 | 코드 리뷰 상태 확인 후 Editor 작업 / 코드 리뷰 |
| 화면 조작 명시 요청 | Editor 역할의 화면 작업 모드 진입 조건 확인과 작업 직전 승인 |
| 코드와 asset의 실제 일치 확인 | Editor 읽기 전용 진단(코드 계약 대조 포함) |
| 진행 중 작업의 PIE 결과 | 통과면 완료 처리, 실패면 같은 작업 폴더에서 진단 |
| 완료된 작업에서 발견한 버그 | 버그 리포트 후 새 `BUG-` 작업 |
| 진행 중 작업 재개 | `CONTEXT.md`와 결과물 첫머리로 현재 단계 판정 |

요청이 속한 작업을 먼저 정한다. 진단 요청을 수정 권한으로 넓히지 않고, 새 사용자 동작이 필요하면 기능 명세로 돌린다.

## 자동 진행과 중단

기능 명세 승인(자동 승인 포함) 뒤 아키텍처 → 구현 → 코드 리뷰 → Editor 작업은 사용자 호출 없이 잇는다. 자동 승인하면 확정본 요지(3~5줄)와 경로를 사용자에게 알리고 바로 진행한다. 워커가 완료를 보고해도 마스터가 결과물과 결론을 확인한 뒤 다음 단계로 간다.

중단 조건: 사용자 결과가 달라지는 선택, 기능 명세 질문지 답변·자동 승인 예외 확인·사용자 PIE 검증, 루프 한도 초과 뒤 아키텍처 자동 복귀도 사용함, 기능 명세 재검토, 화면 작업 승인(매번), 사전 허용 밖 asset 수정·사용자 변경 충돌·새 외부 권한, 빌드 전 사용자 Editor 종료 필요, 작업 ID·시나리오 ID·단계 불일치나 입력 결과물이 `완료`가 아님.

중단 보고에는 완료 범위, 책임 단계, 차단 근거, 필요한 사용자 결정과 재개 지점을 넣고 `CONTEXT.md`에도 남긴다.

## 구현·코드 리뷰 루프

- 리뷰 실패에 따른 재작업은 작업당 2회까지 자동이다. 세 번째 리뷰도 실패하면 같은 지적 반복은 설계 모호로 아키텍처 복귀(이후 새 구현 에이전트), 매번 새 지적은 범위 과대로 아키텍처에서 분할, 사용자 동작 결정은 기능 명세로 보낸다.
- 같은 지적이 반복되면 아키텍처 복귀 전에 구현을 새 구현 에이전트로 한 번 교체할 수 있다.
- 아키텍처 자동 복귀는 작업당 1회이며 복귀 뒤 루프는 새로 센다. 리뷰가 처음부터 설계·명세 문제로 결론 내리면 바로 복귀한다.
- 리뷰 회차, 리뷰 승인 커밋과 아키텍처 자동 복귀 사용 여부를 `CONTEXT.md`에 적는다. 사용자 PIE 실패에서 시작한 재작업은 새로 세고, 같은 PIE 항목이 두 번 실패하면 아키텍처 검토로 보낸다.
- 코드 리뷰나 Editor 작업이 기능 명세·아키텍처로 복귀시키면 복귀 전에 `FEEDBACK_BACKLOG.md`에 RET를 남기고, 복귀 대상·변경 범위·유지되는 완료 범위를 `CONTEXT.md`에 적는다.

## 워커 호출

| 역할 | 실행 | 모델·추론 설정 |
|---|---|---|
| 기능 명세, 아키텍처, 코드 리뷰, Unreal Editor, 회고 | Claude 워커 | `.claude/agents/bathhouse-*.md` |
| C++ 구현 | Claude 워커 | `.claude/agents/bathhouse-implementation.md` |

- 코드 리뷰는 구현과 다른 모델·추론 설정의 독립 에이전트가 맡는다(정의 파일 기준).
- Unreal Editor 역할은 한 에이전트가 전담한다.
- 호출할 때 모델·추론 수준을 넘기지 않고 `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`를 쓰지 않는다. 사용자 지시만 예외이며 `CONTEXT.md`에 적는다.
- 워커는 백그라운드로 실행하고 완료 알림을 받은 뒤 결과를 읽는다. 구현·빌드는 10분을 넘길 수 있다. 짧은 간격으로 폴링하지 않는다.
- 기능 명세 워커가 사전 조사를 요청하면 질문지를 사용자에게 넘기기 전에 Editor 조사를 실행하고, 결과를 같은 기능 명세 워커(재개할 수 없으면 인계받은 새 워커)에 넘겨 질문지에 반영시킨다.

### 재개와 신규

- 재개: 같은 작업·역할의 미완료 작업, 자기 구현의 후속 수정, 같은 리뷰어의 지적에 따른 재작업 후 재검증.
- 신규: 다른 작업·역할, 첫 코드 리뷰, 사용자 PIE 실패 진단(결함을 놓친 원래 리뷰어를 쓰지 않음), 설계의 근본 변경, 과도한 컨텍스트나 반복 오판.
- 재개할 수 없으면(세션 종료로 Claude 워커 ID가 사라짐 등) 같은 역할의 새 워커에 작업 폴더, `CONTEXT.md`와 직전 결과물로 인계한다.
- 호출된 워커는 이후 마스터 대화를 따라오지 않는다. 재개할 때 그 사이의 사용자 결정과 변경을 메시지로 함께 넘긴다.
- Unreal Editor 역할 안에서 MCP·Python·화면 작업 모드를 오가는 것은 새 에이전트 사유가 아니다.

## 인계 패킷과 완료 보고

- 단계 인계 패킷: 작업 ID와 작업 폴더, 단계, 시나리오 ID 구간, 읽을 시스템 문서 목록, 입력 결과물, 단계 시작 커밋, 사용자 결정 요약, 금지 범위.
- 재작업 지시 패킷: 버그 리포트 경로와 작업·시나리오 ID, 승인된 계약과 실제 관찰·재현 조건, 로그·코드·asset 근거, 유입 단계와 검출 실패 단계, 확정 원인 또는 추가 조사 범위, 요청 수정과 금지할 임시 우회, 회귀 검증 조건과 복귀 지점.
- 완료 보고는 결론과 파일 경로 중심 20줄 이내로 받는다. Editor 워커가 보고 뒤에 붙인 `REPORT_UNREAL_*.md` 전문은 수정 없이 저장한다([AGENT_WORKFLOW.md](AGENT_WORKFLOW.md) 소유권 절). 말로만 전달된 중요한 결정은 다음 단계 전에 소유 결과물에 반영시킨다.

## 빌드 전 Editor 확인

구현 워커를 부르기 전에 같은 프로젝트의 Unreal Editor 프로세스를 확인한다. 사용자 Editor가 열려 있으면 Live Coding·모듈 DLL 잠금으로 `Build.bat`이 실패하므로, 사용자에게 저장 후 종료를 요청하고 기다린다. 작업용 Editor는 Editor 단계가 끝날 때 종료돼 있어야 한다.

## 사용자 PIE 인계

1. Editor 작업 뒤 기능 시나리오, 코드 리뷰 결론과 `REPORT_UNREAL_EDITOR.md`가 서로 맞는지 문서로 확인한다.
2. 화면 작업 후보가 있으면 대상·조작·자동화 실패 근거·예상 범위를 보여 주고 작업 직전 승인을 받는다. 승인된 항목만 같은 Editor 에이전트로 처리하고 나머지는 `USER_UNREAL.md`로 남긴다.
3. 구현·Editor 단계의 PIE 관찰 항목으로 `PIE_CHECKLIST.md`(단계 값: 사용자 PIE 검증)를 만든다. 동선 순서로 정렬하고 `이번 변경`과 `회귀 확인`(영향받는 시스템만)으로 나눈다.

```markdown
| # | 구분 | 시나리오 ID | 할 일 | 기대 결과 | 결과 |
|---|---|---|---|---|---|
| 1 | 이번 변경 | SVC4-001 | 상점에서 안마의자 구매 후 개봉 | 설비 아이템이 나온다 | |
```

4. `USER_UNREAL.md` 항목과 `PIE_CHECKLIST.md`를 한 번에 넘긴다. 사용자는 `결과` 칸에 `통과`·`실패: 메모`를 적거나 `전부 통과`, `5번 실패: …`로 짧게 보고한다. 버그 리포트는 마스터가 쓴다.

## 사용자 PIE 실패

- 진행 중 작업의 실패는 버그 리포트를 쓰고 같은 작업 폴더에서 처리한다. 완료된 작업의 버그만 새 `BUG-` 작업으로 연다.
- 먼저 코드 단계 커밋과 Editor 단계 커밋을 나눠 비교해 책임 쪽을 좁힌다. 실패한 단계의 커밋만 되돌린다.
- 새 코드 리뷰어가 원인을 진단한다. 구현 문제면 그 리뷰어가 `PROMPT_IMPLEMENTATION_R.md`를 쓰고 수정 뒤 재검증한다.
- Editor 설정 문제면 Editor 읽기 전용 진단(`REPORT_UNREAL_DIAGNOSIS.md`) 뒤 마스터가 `PROMPT_UNREAL_R.md`(단계 값: Editor 작업)를 쓴다. 코드와 Editor가 각각 계약대로인데 함께 실패하면 같은 진단으로 양쪽 계약을 추적해 책임 단계를 정한다.
- 설계·명세 문제면 R 프롬프트 없이 해당 단계로 복귀한다. PIE에서 발견된 문제는 RET가 아니라 버그 리포트로 기록하고, 통과하면 `수정 결과` 네 줄을 갱신한다([FEEDBACK_POLICY.md](FEEDBACK_POLICY.md)).

## 사전 허용, Git과 작업 전환

- 기능 명세 질문지에서 승인 범위 밖 asset 처리와 PIE 통과 후 커밋·병합 여부를 묻고, 승인 일자(자동/명시)와 함께 `CONTEXT.md`에 적는다. 화면 작업 모드는 사전 허용 대상이 아니다.
- 아키텍처 단계에 들어갈 때 기본 브랜치에서 `work/<작업 ID>`를 만들고 `CONTEXT.md`에 적는다. 기능 명세 결과물이 커밋되지 않았으면 먼저 기본 브랜치에 커밋한다.
- 단계가 끝날 때마다 `[작업 ID] 단계: 요약`으로 커밋하고 단계 시작 커밋을 `CONTEXT.md`에 적는다. 리뷰는 `git diff <단계 시작 커밋>`을 읽는다.
- 사용자 PIE 통과 뒤 `--no-ff`로 병합한다(사전 허용이 없으면 먼저 묻는다). Editor가 열린 상태에서는 브랜치를 바꾸지 않는다.
- 코드·Editor 단계의 작업은 동시에 하나만 둔다. 전환은 단계 경계 커밋, 현재 작업 `보류`, Editor 종료 또는 dirty 없음 확인 뒤 사용자 지시가 있을 때만 한다. 문서만 다루는 병렬 작업은 별도 git worktree에서 한다.

## 기록과 회고

버그 리포트, RET와 회고·승격은 [FEEDBACK_POLICY.md](FEEDBACK_POLICY.md)를 따르며 일반화와 승격은 사용자가 요청할 때만 한다. 에이전트 선택·단계·인계 실패는 오케스트레이터 책임으로 회고 대상에 남긴다.
