# 버그 기록과 피드백 정책

## 목적

버그 기록, 상위 단계 복귀 기록과 역할별 피드백의 형식·작성 시점·적용 범위를 정한다. 단계·승인·결과물 소유권은 [AGENT_WORKFLOW.md](AGENT_WORKFLOW.md)를 따른다.

## 기록 계층

| 위치 | 내용 | 작성 |
|---|---|---|
| `BugReports/<보고일>_<요약>.md` | 사용자가 관찰한 개별 버그 현상과 수정 결과 네 줄 | 마스터(사용자 보고 기반) |
| `Work/<작업 ID>/` | 원인 분석과 수정 내용(작업 결과물) | 각 단계 |
| `FEEDBACK_BACKLOG.md` 일반화 항목 | 여러 사건에서 일반화한 역할별 경험적 교훈 | 사용자가 요청한 회고 세션 |
| `FEEDBACK_BACKLOG.md` 상위 단계 복귀 기록 | 코드 리뷰·Editor 작업이 기능 명세·아키텍처로 돌려보낸 사건 | 마스터 |
| `AGENT_*.md` | 권한, 절대 금지, 승인 관문, 결과물 소유권 같은 안정적인 역할 계약 | 사용자가 요청한 세션(승인 후) |
| `Architecture/*`, `Unreal/*` | 해결 후 확정된 현재 구조. 버그 이력은 두지 않는다 | 소유 단계 |

버그 기록, 복귀 기록과 일반화 항목은 Git 이력과 함께 회고의 입력이다. 일반 에이전트는 전체 버그 목록과 복귀 기록을 기본으로 읽지 않는다.

## 버그 기록

- 파일 하나에 버그 하나다. 보고일, 발견 경로, 상태, 현상, 재현 조건, 기대 동작, 실제 동작, 영향 범위, 재현 빈도와 미확인 항목을 적는다.
- 사용자가 관찰한 현상만 적는다. 사용자의 짧은 PIE 보고(`5번 실패: …`)를 마스터가 이 형식으로 옮긴다.
- 진행 중 작업의 PIE 실패도 버그 리포트를 쓴다. 처리는 같은 작업 폴더에서 한다. 완료된 작업에서 나중에 발견한 버그만 새 `BUG-` 작업을 연다.
- 사용자 PIE 재검증을 통과하면 마스터가 상태 줄을 갱신하고 맨 아래에 다음 네 줄만 덧붙인다. 내용은 수정 작업의 완료 보고에서 옮기며 새로 분석하지 않는다.

```markdown
## 수정 결과

- 원인: <확정 원인 한 줄>
- 유입 단계: <결함이 들어온 단계와 작업·커밋>
- 검출 실패 단계: <원래 잡았어야 할 단계와 놓친 이유 한 줄>
- 수정 커밋: `<커밋 해시>`
```

- 사용자 PIE에서 발견된 설계·명세 문제도 복귀 기록이 아니라 버그 리포트로 기록한다.

## `FEEDBACK_BACKLOG.md` 구조

1. 마지막 회고 기준점(날짜와 커밋)
2. 일반화 항목 색인: Feedback ID, 역할 태그, 시스템 태그, 상태
3. 일반화 항목
4. 상위 단계 복귀 기록
5. 이전 형식 기록(FB-001~): 채택 전에 쌓인 원문 기록. 회고에서 검토해 일반화 항목의 근거로 연결한 뒤 제거한다.

역할 태그는 `ORCHESTRATOR`, `FEATURE_SPEC`, `ARCHITECTURE`, `IMPLEMENTATION`, `REVIEW`, `UNREAL_EDITOR`다. Computer Use 화면 작업 모드의 교훈은 `UNREAL_EDITOR`를 쓴다.

## 일반화 항목 형식

```markdown
### FBK-<번호> <한 줄 요약>

- 상태: Experimental | Active | Retired
- 역할 태그: <하나 이상> / 시스템 태그: <관련 시스템>
- 재발 패턴과 적용 범위:
- 유입 단계와 원래 검출했어야 할 게이트:
- 잘못된 판단이 만드는 위험:
- 권장 행동과 검증 방법:
- 근거: <버그 리포트 경로와 수정 커밋 | RET ID | 작업 ID와 커밋>
- 적용하지 않을 조건:
```

- Feedback은 경험적 지침이며 `AGENT_*.md`와 충돌하면 역할 계약이 우선한다. 안전, 권한, 필수 승인과 결과물 소유권은 `AGENT_*.md`에 둔다.
- 특정 Actor 이름, 당시 좌표와 임시 해결값은 일반화 항목에 넣지 않고 버그 리포트나 작업 결과물에 둔다.

## 상위 단계 복귀 기록 (RET)

코드 리뷰나 Editor 작업 결과 기능 명세 또는 아키텍처로 재작업이 결정되면, 마스터가 복귀 실행 전에 남긴다. 내용은 리뷰 결과물이나 Editor 작업 보고에서 옮기며 새로 분석하지 않는다. Editor 도구의 기능 한계(MCP·Python 미지원 등)는 설계 결함이 아니므로 대상이 아니다.

```markdown
### RET-<번호> <한 줄 요약>

- 일자·작업 ID: <날짜>, `<작업 ID>`
- 발견 단계: 코드 리뷰 | Editor 작업
- 복귀 대상: 기능 명세 | 아키텍처 (루프 한도 초과 복귀면 함께 표시)
- 문제: <드러난 상위 단계 결함 한 줄>
- 놓친 이유: <해당 단계에서 왜 정하지 못했거나 잘못 정했는지 한 줄>
- 검출 실패 단계: 코드 리뷰 | Editor 사전 조사 미요청 | 없음(Editor에서만 확인 가능) — 발견 단계가 Editor 작업일 때만
- 근거: <리뷰 결과물 또는 Editor 작업 보고 경로와 해당 시점 커밋>
```

Editor 작업에서 발견된 복귀의 검출 실패 단계 판정:

| 드러난 사실이 코드 리뷰 시점에 어디 있었나 | 검출 실패 단계 |
|---|---|
| `Unreal/*System.md` 또는 사전 조사 보고에 이미 있었음 | 코드 리뷰 |
| 문서에 없었고 실제 asset을 봐야만 알 수 있었음 | Editor 사전 조사 미요청 |
| Editor에서만 일어나는 엔진 경로(재인스턴싱, 저장·재로드 등) | 점검 항목으로 볼 수 있었으면 코드 리뷰, 아니면 없음 |

복귀 기록은 작업 지침이 아니다. 상태 없이 쌓아 두고 사용자가 요청한 회고에서만 검토한다. 검토를 마친 기록은 일반화 항목의 근거로 연결한 뒤 제거한다.

## 로딩 규칙

- 워커는 색인에서 자기 역할 태그와 현재 시스템에 맞는 `Active` 항목만 찾아 적용한다.
- `Experimental` 항목은 마스터가 현재 작업의 검증 대상으로 명시했을 때만 적용한다.
- `Retired` 항목, 복귀 기록과 이전 형식 기록은 일반 작업에서 읽지 않는다.
- Feedback을 적용하지 않는 편이 맞으면 적용 제외 조건과 근거를 완료 보고에 남긴다.

## 회고와 승격

피드백 일반화, `FEEDBACK_BACKLOG.md` 등록·상태 변경과 `AGENT_*.md` 승격은 사용자가 요청할 때만 한다. 작업 완료, 버그 수정이나 반복 실패를 이유로 자동 실행하지 않는다.

```text
[평소] 워커가 완료 보고에 원인과 유입 단계를 남기고, 마스터가 버그 리포트 수정 결과와 RET를 쓴다
[사용자 요청] 회고 워커가 기준점 이후의 버그 리포트 수정 결과·RET·이전 형식 기록에서 반복 패턴과 후보를 분석한다
→ 요청받은 세션이 중복·충돌·과적합과 비용을 심사한다
→ 사용자에게 후보를 보고하고 승인받는다
→ 요청받은 세션이 승인된 항목만 FEEDBACK_BACKLOG.md 또는 AGENT_*.md에 반영하고 기준점을 갱신한다
```

- 회고 워커는 후보를 제안만 한다. 워커에게 `FEEDBACK_BACKLOG.md` 일반화 항목과 `AGENT_*.md` 수정 권한을 주지 않는다.
- 새 교훈은 `Experimental`로 등록하고, 이후 회고에서 유효성을 확인해 `Active` 유지, `AGENT_*.md` 승격 또는 `Retired`로 처리한다.
- 안전 또는 항상 지켜야 할 불변 계약만 `AGENT_*.md`로 승격한다. 반영 세션은 문서 크기·중복 규칙을 확인한다.
- 반영 항목은 표현 명확화 같은 저위험 정리를 포함해 모두 사용자 승인을 받는다. 회고는 사용자가 요청할 때만 하므로 승인은 그 자리에서 받는다.

다음 중 두 개 이상이면 일반화 후보로 본다.

1. 다른 기능에서도 재발할 가능성이 있다.
2. 특정 asset이나 수치가 아닌 일반 계약으로 표현할 수 있다.
3. 항상 확인하면 재작업 비용을 줄일 수 있다.
4. 기존 리뷰나 테스트로 검출할 수 있었던 문제다.
