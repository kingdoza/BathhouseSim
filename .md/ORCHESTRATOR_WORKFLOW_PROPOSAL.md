# BathhouseSim 오케스트라 워크플로우 제안

## 상태와 목적

- 상태: 논의안. 아직 `AGENT_WORKFLOW.md`를 대체하거나 에이전트 권한을 변경하지 않는다. 현재 정본은 `AGENTS.md`, `.md/AGENT_WORKFLOW.md`와 역할별 `.md/AGENT_*.md`다.
- 목적: 하나의 마스터 대화에서 전문 에이전트 호출, 승인 관문, 재작업, 컨텍스트 전달, 후속 문제 기록과 개선 사이클을 관리하는 방식을 제안한다.
- 이 제안서는 합의 내용의 완결성을 우선하며 공통 정책 문서의 200줄 제한을 적용하지 않는다. 채택할 때는 내용 삭제 대신 안정적인 책임 단위로 문서를 분리한다.

## 기본 원칙

1. 사용자는 단계나 에이전트 이름을 지정하지 않아도 되며 마스터가 요청 의도와 현재 상태로 선택한다.
2. 기능 명세 승인 뒤에는 차단 사유가 없는 한 설계부터 통합 리뷰까지 자동으로 연결한다.
3. 대화는 편의용 컨텍스트이고 단계 간 정본 전달은 프로젝트 문서로 수행한다.
4. 전문 에이전트는 역할 범위를 넘지 않으며, 후속 문제는 유입·검출 실패 단계를 구분해 일반화된 교훈만 미래 에이전트에 제공한다.

## 사용자 요청 자동 분류

| 사용자 요청 | 마스터가 선택할 시작 단계 |
|---|---|
| 신규 기능 구현 | 기능 명세 |
| 원인과 해결법만 요청 | 관련 Source·Editor 읽기 전용 진단 |
| 승인된 범위의 코드 수정 | 구현 |
| Editor 작업 요청 | 코드 리뷰 상태 확인 후 Unreal MCP |
| 화면 조작 명시 요청 | Computer Use 진입 조건 확인 |
| 코드 검토 | 코드 리뷰 |
| 코드와 asset의 실제 일치 확인 | 통합 리뷰 |
| 플레이 후 버그·의도 불일치 보고 | 문제 분류 후 책임 단계 복귀 |

- 사용자가 단계를 잘못 지정해도 마스터가 진입 조건을 확인하고 올바른 단계로 교정한다.
- 진단 요청은 수정 권한으로 확대하지 않고, 수정 요청은 승인된 기능·설계 범위 안에서만 실행한다.
- 새로운 사용자 동작이나 결과를 결정해야 하면 기존 구현을 임의로 확장하지 않고 기능 명세로 돌린다.

## 마스터 오케스트레이터 책임

- 요청을 분류하고 현재 단계의 진입 조건과 필수 결과물을 확인한다.
- `기능 ID + 역할` 단위로 하위 에이전트를 관리하고 재개 또는 신규 생성을 판단한다.
- 새 사용자 결정과 중요한 변경사항을 관련 문서 또는 후속 메시지로 전달한다.
- 리뷰 실패는 구현, 구조 문제는 아키텍처, 동작 불일치는 기능 명세로 돌려보낸다.
- MCP 미지원 작업을 Computer Use로 자동 전환하지 않는다.
- 사용자 승인 관문, 외부 권한과 실제 차단 사유에서만 자동 진행을 멈춘다.
- 최종적으로 기능 계약, 코드, 저장된 Editor 상태와 검증 결과의 일치를 확인한다.

## 에이전트별 고정 모델과 추론 수준

| 역할 | 모델 | 추론 수준 |
|---|---|---|
| 마스터 오케스트레이터 | `gpt-6-astra` | `high` |
| 기능 명세 | `gpt-6-astra` | `high` |
| Unreal MCP 사전 조사·Editor 작업 | `gpt-5.6-terra` | `medium` |
| 아키텍처 | `gpt-6-astra` | `high` |
| C++ 구현 | `gpt-5.6-sol` | `high` |
| 코드 리뷰 | `gpt-6-astra` | `high` |
| Computer Use | `gpt-6-astra` | `high` |
| 통합 리뷰 | `gpt-6-astra` | `high` |
| 회고·피드백 일반화 | `gpt-6-astra` | `high` |

작업 난이도에 따른 자동 추론 상·하향은 사용하지 않는다. 모델이나 추론 수준 변경은 사용자의 명시적 요청 또는 워크플로우 정책 개정으로만 수행한다.

## 정규 실행 흐름

```text
요청 → 기능 명세 → 선택적 MCP 사전 조사 → 사용자 명세 승인
→ 아키텍처 → 구현 → 코드 리뷰 → MCP Editor 작업
→ 선택적 수동/Computer Use → 통합 리뷰 → 수직 플레이 승인 또는 완료
```

- 기능 명세 승인 전에는 설계와 구현을 시작하지 않는다.
- 승인 후 `설계 → 구현 → 코드 리뷰 → MCP → 통합 리뷰`는 별도 사용자 호출 없이 이어서 진행한다.
- 질문, 리뷰 실패, MCP 기능 부족, 필수 수동 작업 또는 사용자 승인 관문에서는 중단하고 정확한 재개 조건을 남긴다.

## 자동 진행과 중단 조건

다음 단계의 진입 조건, 입력 결과물과 권한이 충족되면 마스터는 사용자에게 다시 실행을 요청하지 않고 다음 에이전트를 호출한다. 전문 에이전트가 완료 보고를 반환했다고 해서 다음 단계가 자동 승인된 것은 아니며 마스터가 결과물과 결론을 확인한다.

자동 진행을 중단하는 조건은 다음과 같다.

- 사용자 결과가 달라지는 선택이 남음
- 기능 명세 승인 또는 수직 구현 플레이 승인이 필요함
- 리뷰가 재작업·설계 재검토·기능 명세 재검토를 결정함
- MCP 기능 부족으로 필수 Editor 작업이 `USER_UNREAL.md`에 남음
- 사용자 소유 변경과 충돌하거나 새로운 외부 권한이 필요함
- 결과물의 작업 ID, 시나리오 ID 또는 현재 단계가 서로 일치하지 않음

중단 보고에는 완료된 범위, 책임 단계, 차단 근거, 필요한 사용자 결정과 재개 지점을 포함한다.

## 수직 구현

입력, UI, Content, Actor lifecycle, 물리, collision, Navigation 또는 여러 대상의 공통화가 함께 바뀌면 대표 대상 하나의 사용자 흐름 전체를 먼저 완성한다.

```text
대표 시나리오 명세 → 설계 → 구현 → 코드 리뷰 → Editor 작업 → 통합 리뷰
→ 사용자 플레이 승인 → 전체 확장 설계부터 동일 흐름 반복
```

- 일부 C++ 계층만 만드는 것은 수직 구현이 아니다.
- 사용자 승인 전에는 다른 설비·아이템·상태로 동작을 일반화하지 않는다.
- 단순 계산, 로그 또는 Content 비의존 내부 버그는 근거를 남기고 전체 수정 경로를 사용할 수 있다.

## 컨텍스트와 인계

- 마스터는 현재 대화의 이전 결정과 진행 상황을 유지하고 새 하위 에이전트에 필요한 컨텍스트와 문서를 전달한다.
- 이미 호출된 하위 에이전트는 이후 마스터 대화를 자동으로 동기화하지 않는다.
- 같은 하위 에이전트를 재개하면 그 에이전트의 이전 작업 컨텍스트를 이어서 사용한다.
- 중요한 결정은 정기 결과물과 정본 문서에 반영하며, 새 요구사항은 후속 메시지나 갱신 문서로 전달한다.

## 단계 인계 계약

각 에이전트의 완료 보고와 다음 단계 프롬프트에는 최소한 다음을 포함한다.

- 기능 ID, 현재 단계와 관련 시나리오 ID
- 읽은 정본과 입력 결과물
- 수행한 변경 또는 조사 범위
- 확정한 내용과 다음 역할이 결정해야 할 내용
- 검증한 항목, 실패와 미검증 항목
- 사용자 소유 변경, dirty package와 저장 상태
- 결론: 완료, 재작업, 상위 단계 복귀 또는 사용자 결정 필요

마스터는 말로만 전달된 중요한 결정을 다음 단계에 넘기기 전에 소유 결과물에 반영한다. 새 에이전트에는 전체 대화를 무조건 복제하기보다 현재 정본, 작업 결과물과 필요한 결정 요약을 전달한다.

## 기존 에이전트와 새 에이전트 선택

기본 기준은 `연속성이 필요하면 기존 에이전트, 독립성이 필요하면 새 에이전트`다.

### 기존 에이전트 재개

- 동일 기능·역할의 미완료 작업, 자신이 만든 구현의 후속 수정
- 직전 결과 질문, 리뷰 지적 반영 또는 기존 판단 과정이 필요한 원인 분석

### 새 에이전트 생성

- 독립된 신규 기능·다른 역할 또는 선입견 없는 코드·통합 리뷰
- 요구사항·설계의 근본 변경, 과도한 컨텍스트 또는 잘못된 가정 반복
- 복수 대안을 독립적으로 비교하거나 병렬 처리하는 경우

구현 후속 수정은 기존 구현 에이전트가 맡고, 재승인은 별도의 리뷰 에이전트가 맡는 것을 기본으로 한다.

판단 순서는 다음과 같다.

```text
같은 기능·같은 책임인가?
├─ 아니오: 새 에이전트
└─ 예
   ├─ 독립 검토가 필요한가: 새 에이전트
   ├─ 요구사항이 근본적으로 바뀌었는가: 새 에이전트
   ├─ 기존 컨텍스트가 과도하거나 반복 오판하는가: 새 에이전트
   └─ 나머지: 기존 에이전트 재개
```

기존 에이전트의 컨텍스트가 필요하지만 독립 검토도 필요하면 담당 에이전트가 수정하고 별도 리뷰 에이전트가 검증한다.

## Unreal 실행 경계

- Unreal MCP는 읽기 전용 사전 조사와 코드 리뷰 승인 후 Editor 작업에 사용한다.
- MCP 에이전트는 Computer Use, 화면 좌표 조작과 `.uasset` 직접 편집을 사용하지 않는다.
- MCP로 불가능한 실제 Editor 작업은 한국어 `.md/USER_UNREAL.md`에 exact 경로, 조작, 기대 결과와 재개 조건을 기록한다.
- Computer Use는 사용자가 현재 작업에서 명시적으로 요청한 경우에만 별도 역할로 실행한다.
- Editor 변경은 allowlist asset만 Compile, 개별 Save, 재로드하고 관련 `.md/Unreal/*System.md`를 실제 저장 상태로 갱신한다.

## 후속 문제 분류와 복귀

| 문제 유형 | 책임 단계 | 기본 처리 |
|---|---|---|
| 승인된 동작과 다른 코드 실행 | 구현 | 기존 구현 에이전트 수정 후 코드 리뷰 |
| Blueprint·Level·StateTree 설정 오류 | Unreal MCP | Unreal 재작업 후 통합 리뷰 |
| 상태 owner·좌표·lifecycle 구조 오류 | 아키텍처 | 재설계 후 구현부터 반복 |
| 문서대로 구현됐지만 사용자 기대와 다름 | 기능 명세 | 동작 계약을 다시 승인 |
| 코드와 Editor가 각각 맞지만 함께 실패 | 통합 | 양쪽 계약을 추적해 책임 단계로 반환 |
| 기존 범위 밖의 개선 요구 | 기능 명세 | 신규 기능으로 시작 |
| 에이전트 선택·단계·인계 실패 | 오케스트레이터 | 워크플로우 회고 대상으로 기록 |

## 즉시 피드백 형식

마스터는 담당 에이전트에 단순 재작업 명령 대신 다음 내용을 전달한다.

- 문제 ID와 관련 기능·시나리오 ID
- 승인된 계약과 실제 관찰 결과
- 로그, PIE, 코드 또는 asset 근거
- 확정된 책임 단계와 근본 원인, 미확정이면 조사 범위
- 요청하는 수정 결과와 금지할 임시 우회
- 회귀 검증 조건과 워크플로우 복귀 지점

찐빠를 낸 에이전트는 사건과 원인을 보고할 수 있지만 자기 판단만으로 공통 지침을 추가하지 않는다.

예시 피드백 패킷은 다음과 같다.

```text
[문제 ID / 기능 ID / 시나리오 ID]
[승인된 계약]
[실제 관찰과 재현 조건]
[로그·PIE·코드·asset 근거]
[유입 단계 / 검출 실패 단계]
[확정 원인 또는 추가 조사 범위]
[요청 수정 / 금지할 임시 우회]
[회귀 검증 / 복귀 지점]
```

## 기록 계층 제안

```text
.md/Retrospective/INCIDENTS.md
.md/Feedback/{0_FEEDBACK,ORCHESTRATOR,FEATURE_SPEC,ARCHITECTURE,
IMPLEMENTATION,REVIEW,UNREAL_MCP,COMPUTERUSE,INTEGRATION_REVIEW}.md
```

- `Retrospective/INCIDENTS.md`: 개별 사건의 증상, 의도, 재현, 원인, 해결과 검증 이력
- `Feedback/*.md`: 여러 사건에서 일반화된 역할별 경험적 교훈
- `AGENT_*.md`: 권한, 절대 금지, 승인 관문과 결과물 소유권 같은 안정적인 역할 계약
- `Architecture/*`와 `Unreal/*`: 버그 이력이 아니라 해결 후 확정된 현재 구조
- `USER_UNREAL.md`: 현재 남은 실제 Editor 수동 작업만 유지

각 에이전트는 자기 역할의 Feedback 파일만 기본 대상으로 삼고, 원본 사건 전체는 관련 진단이나 회고 때 태그로 조회한다.

## Incident 기록 형식

개별 사건에는 다음을 기록한다.

- Incident ID, 기능·시나리오 ID, 관련 시스템 태그
- 사용자가 승인한 의도와 실제 관찰 결과
- 재현 조건과 증거
- 유입 단계와 원래 검출했어야 할 게이트
- 확정된 근본 원인과 수정 내용
- 회귀 검증과 상태: `Investigating`, `Resolved`, `Recurred`
- 일반화 후보 Feedback ID 또는 일회성으로 남긴 근거

사건 기록은 작업 지침이 아니다. 일반 에이전트는 전체 사건 목록을 기본으로 읽지 않으며 마스터나 회고 에이전트가 관련 태그로 필요한 사건만 조회한다.

## 역할별 피드백 형식

각 일반화 항목에는 다음을 기록한다.

- Feedback ID와 상태: `Experimental`, `Active`, `Retired`
- 재발 패턴과 적용 범위
- 잘못된 판단이 만드는 위험
- 권장 행동과 검증 방법
- 근거가 된 Incident ID
- 적용하지 않을 조건

Feedback은 경험적 지침이며 `AGENT_*.md`와 충돌하면 역할 계약을 우선한다. 안전, 권한, 필수 승인과 결과물 소유권은 Feedback이 아니라 `AGENT_*.md`에 둔다.

## Feedback 로딩과 정리

- `0_FEEDBACK.md`는 역할, 시스템 태그, 상태와 해당 파일 위치만 제공하는 색인이다.
- 전문 에이전트는 자기 역할과 현재 시스템에 관련된 `Active` 항목만 기본 적용한다.
- `Experimental` 항목은 마스터가 현재 작업의 검증 대상으로 명시했을 때 적용한다.
- `Retired` 항목은 일반 작업에서 읽지 않고 제거 또는 기록 보관 대상으로 처리한다.
- 같은 원인의 Feedback은 병합하고 특정 asset 이름·당시 좌표·임시 수치는 Incident에만 둔다.
- Feedback 파일이 커지면 현재 유효한 판단만 남기고 시스템 태그나 안정적인 책임 기준으로 분리한다.
- Feedback을 적용하지 않는 편이 맞으면 에이전트가 적용 제외 조건과 근거를 완료 보고에 남긴다.

## 일반화와 승격 책임

```text
담당 에이전트가 사건·원인 기록
→ 회고 에이전트가 반복 패턴과 일반화 후보 분석
→ 마스터가 중복·충돌·과적합과 비용을 심사
→ 필요한 경우 사용자 승인
→ 지침서 담당 단계가 Feedback 또는 AGENT 문서에 반영
```

- 회고 에이전트는 승격 후보를 제안하며 단독으로 확정하지 않는다.
- 기존 역할의 검증 항목 명확화와 저위험 Feedback은 마스터가 승인하고 보고할 수 있다.
- 새 단계, 새 결과물, 승인 관문, 권한 변경, 역할 재분배와 프로젝트 전체 비용 증가는 사용자 승인을 받는다.
- 안전 또는 항상 지켜야 할 불변 계약만 Feedback에서 `AGENT_*.md`로 승격한다.

사용자 승인이 필요한 변경은 새 단계·결과물·승인 관문, 에이전트 권한, 역할 책임, MCP와 Computer Use 경계 또는 프로젝트 전체 작업 비용을 바꾸는 경우다. 기존 계약을 바꾸지 않는 표현 명확화와 저위험 Feedback 정리는 마스터가 처리하고 결과를 보고할 수 있다.

## 워크플로우 개선 사이클

```text
버그·의도 불일치 발생
→ 증상과 재현 조건 기록
→ 유입 단계와 검출 실패 단계 분리
→ 책임 에이전트 수정
→ 독립 에이전트 재검증
→ 사건 종료와 회귀 기준 기록
→ 반복성·일반성 평가
→ 역할별 Feedback에 Experimental 등록
→ 이후 작업에서 유효성 확인
→ Active 유지, AGENT 계약 승격 또는 Retired 처리
```

다음 중 두 개 이상이면 일반화 후보로 본다.

1. 다른 기능에서도 재발할 가능성이 있다.
2. 특정 asset이나 수치가 아닌 일반 계약으로 표현할 수 있다.
3. 항상 확인하면 재작업 비용을 줄일 수 있다.
4. 기존 리뷰나 테스트로 검출할 수 있었던 문제다.

단일 사건의 구체적인 Actor 이름, 당시 좌표와 임시 해결값은 Feedback이나 `AGENT_*.md`로 승격하지 않는다.

## 선택적 오케스트레이션 Skill

필요하면 별도의 `SKILL.md`를 진입점으로 만들어 자연어 요청에서 이 흐름을 시작하고 단계 전환을 자동화한다. Skill은 현재 단계 판정, 호출·재개, 승인 관문과 복귀만 담당하고, 프로젝트 규칙을 복제하지 않은 채 `AGENTS.md`, `AGENT_WORKFLOW.md`와 역할별 지침을 읽는다. 프로젝트 문서가 정본이며 Skill은 실행기다.

## 채택 시 필요한 후속 작업

1. 마스터 오케스트레이터의 역할과 자동 전환 규칙을 별도 지침으로 확정한다.
2. 역할별 Feedback 정책과 사건 기록의 태그·상태·종료 형식을 확정한다.
3. 회고 권한과 승인 기준을 정하고 `AGENT_WORKFLOW.md`에는 라우팅과 필수 경계만 반영한다.
4. 필요할 경우 오케스트레이션 Skill을 추가하되 정본 내용을 중복하지 않는다.
